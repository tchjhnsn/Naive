## What this is

The modules that compose routes. Each one runs records through the router's `call`, so it sits in the interface, above `schema/` and the router. They moved here from `schema/` in step 3 of the router inversion in the monorepo rebuild. Leaving them in `schema/` kept an import from `schema/` up to `packages/naive/src/router/router.mjs`, and that import was part of the cycle. The design is [`docs/design/MONOREPO_ROUTER_INVERSION_2026-11-05.md`](../../../../../docs/design/MONOREPO_ROUTER_INVERSION_2026-11-05.md). No shim stays at the old paths, because a shim would import the interface from `schema/` again.

## Where things are

| Path | Holds |
|---|---|
| [`triggers.mjs`](./triggers.mjs) | Triggers that run after each write (M-12, E-7). A failed run is raised as a decision. `mentura triggers` shows them. |
| [`setup.mjs`](./setup.mjs) | Setup in the model's harness (EE-083). It holds the questions, and each answer is a proposal the founder confirms. `naive setup` and the MCP setup tools use it. Pointing a function at a system runs the system's sync command when the app names one ([`packages/naive/src/core/sync.mjs`](../../core/sync.mjs)), and the state lists those systems under `syncs`. |
| [`migrate-venture.mjs`](./migrate-venture.mjs) | `naive migrate` (EE-076). An agent rewrites a project as records, and each record is written through the router once a person decides. Hosted, `runAgent` refuses: the host passes its agent to `plan(from, dir, { agent })`. |
| [`releases.mjs`](./releases.mjs) | The release rules (I-17, C-13): confirmed records frozen in, live holes named, the release card. |
| [`build-release.mjs`](./build-release.mjs) | `naive build`, the command line over `releases.mjs`. |
| [`venture-package.mjs`](./venture-package.mjs) | The venture package with the idea map's routing (EE-067, EE-061): `venturePackage(dir)` passes `route()` from the idea map into `packages()` in `packages/naive/src/engine/packages.mjs`, and it holds the command line for the `system/package` route. |
| [`signals.ts`](./signals.ts) | The signal pull (signal library design, build item 5), at router level because only router code may act as the signal projector (`asProjector`). The signal engine [`packages/naive/src/engine/signals.ts`](../../engine/signals.ts) reads and decides; this commits. `pull` reads the log lines each library published after the cursor (`.naive/signals.json`), finds the touched subjects (a new signal names one, a new signal withdraws one a projected record cites, or after the cursor a person or another agent wrote a record in a collection a listener reads the ids of, or a fact file a projected record cites), renders them, and diffs: a new or changed record is written through the router as the projector with `derived_from` set to the cited signal addresses and fact files, an unchanged one is verified through freshness and not rewritten, a record a projection writes once and a person now owns is kept, a proposal goes through `propose` in [`decisions.mjs`](../../engine/decisions.mjs) unless its id exists, and a mark through `mark` in [`stale.mjs`](../../engine/stale.mjs) unless it was made. Facts a predicate reads are read through the router as the projector. The cursor moves only after every write succeeded, and the projector's own provenance lines touch nothing, so a pull after a pull writes nothing. `explain` gives one signal at every listener, `replay` renders every projected record again and reports drift without writing, and `emit` writes a person's signal and its log line to the local library `raw/signals/`, refusing props that do not match the type; the same signal emitted twice is written once. The routes are `system/signals` (pull), `system/signals/replay` and `system/signals/explain`; the commands are `naive signals emit|pull|explain|replay`. Withdrawing a decision a retracted signal raised is not built. |
| [`recipe-search.ts`](./recipe-search.ts) | `naive recipes search <pattern>`, knob descent with no model (autoresearch build plan item 10). Coordinate descent over the knobs of the recipe at `recipes/<pattern>`: for each knob in name order it tries one step each way (`stepsOf` in [`packages/naive/src/engine/recipes/knobs.ts`](../../engine/recipes/knobs.ts)), each step the tip's source with that one value rewritten (`setKnob`), checked to read back through the sandbox as that knob alone changed, and written to the recipe route as the agent `knob-search`, so the router scores it against the tip and an agent's keep is held as a draft, which goes live only when a person accepts it with `mentura accept recipes/<pattern>` and its holdout check (build plan item 8). A keep moves the tip and the search goes to the next knob; a pass that keeps nothing takes the square root of the step factor, up to `--shrinks` times. It stops when no step is kept at the smallest step, when the plan's dev budget is spent, at `--max-writes`, or on a refusal with no verdict. A candidate the plan's log has already scored is not written again. It never supplies a score and calls no model. A list, and a string that is not a rating floor, have no step. |
| [`model-steps.mjs`](./model-steps.mjs) | Model steps (use model, EE-073): the payload code computes, the judgments a model still owes, and how code accepts, overrules or routes each answer. The route is `system/steps`. Hosted, `MENTURA_MODEL_CMD` is ignored and the host passes `ask` to `run`. |

## Run and test

- `node packages/naive/src/router/orchestration/triggers.mjs <venture dir> --fire` runs the triggers once.
- `node packages/naive/src/router/orchestration/build-release.mjs <venture dir> [--dry-run] [--json]` builds a release.
- `node packages/naive/src/router/orchestration/migrate-venture.mjs --from <project> --venture <dir>` writes a migration plan.
- `node packages/naive/src/router/orchestration/venture-package.mjs <venture> [--write] [--json]` prints or writes the venture package.
- `node packages/naive/src/router/orchestration/signals.ts <venture dir> pull|replay|explain <signal id>|emit <type> --props '<json>' [--now <iso>] [--json]` runs the signal library; [`packages/naive/src/interfaces/tests/signals-pull-test.ts`](../../interfaces/tests/signals-pull-test.ts) tests it end to end over two ventures.
- `node packages/naive/src/router/orchestration/recipe-search.ts <venture dir> <pattern> [--factor 2] [--shrinks 2] [--max-writes 200] [--json]` runs the knob search; [`packages/naive/src/interfaces/tests/recipe-search-test.ts`](../../interfaces/tests/recipe-search-test.ts) shows a fixture venture improving with no model.
- These tests cover them: [`packages/naive/src/interfaces/tests/setup-test.mjs`](../../interfaces/tests/setup-test.mjs), [`packages/naive/src/interfaces/tests/model-steps-test.mjs`](../../interfaces/tests/model-steps-test.mjs), [`packages/naive/src/interfaces/tests/delegation-test.mjs`](../../interfaces/tests/delegation-test.mjs), [`packages/naive/src/engine/releases-test.mjs`](../../engine/releases-test.mjs), [`packages/naive/src/engine/upgrades-test.mjs`](../../engine/upgrades-test.mjs) (triggers) and [`packages/naive/src/engine/migrate-test.mjs`](../../engine/migrate-test.mjs). The tests in `schema/` start these modules as child processes and do not import them. `node test.mjs` runs all of them.

## How it connects

- Called by: [`packages/naive/src/interfaces/cli/mentura.mjs`](../../interfaces/cli/mentura.mjs), [`packages/naive/src/interfaces/cli/naive.mjs`](../../interfaces/cli/naive.mjs), [`packages/naive/src/interfaces/mcp/server.mjs`](../../interfaces/mcp/server.mjs), [`packages/naive/src/interfaces/dev/setup.mjs`](../../interfaces/dev/setup.mjs) and [`packages/naive/src/router/kit-boundary.mjs`](../kit-boundary.mjs). [`packages/naive/src/core/provenance.mjs`](../../core/provenance.mjs) starts `triggers.mjs` by its path after every write. [`packages/naive/src/engine/workspace-init.mjs`](../../engine/workspace-init.mjs) starts `migrate-venture.mjs` the same way.
- Calls: [`packages/naive/src/router/router.mjs`](../router.mjs), and modules in `schema/`, `packages/` and `knowledge/`. `migrate-venture.mjs` reads each record type's schema with `recordPath` and `releases.mjs` names it to the validator with `schemaNameOf`, both from [`packages/naive/src/records`](../../records/README.md), so neither depends on where the record types sit.

`releases.mjs` checks each released record against its schema in process with `validateFile` from [`packages/naive/src/records/validate.mjs`](../../records/README.md).
