## What this is

The modules that compose routes. Each one runs records through the router's `call`, so it sits in the interface, above `schema/` and the router. They moved here from `schema/` in step 3 of the router inversion in the monorepo rebuild. Leaving them in `schema/` kept an import from `schema/` up to `packages/naive/src/router/router.ts`, and that import was part of the cycle. The design is [`docs/design/MONOREPO_ROUTER_INVERSION_2026-11-05.md`](../../../../../docs/design/MONOREPO_ROUTER_INVERSION_2026-11-05.md). No shim stays at the old paths, because a shim would import the interface from `schema/` again.

## Where things are

| Path | Holds |
|---|---|
| [`triggers.ts`](./triggers.ts) | Triggers that run after each write (M-12, E-7). A failed run is raised as a decision. `mentura triggers` shows them. Each trigger runs once per event, across a crash too (EE-161, phase 12d): a run is keyed by its trigger and event, the key is in the route call's provenance note, and a runner that stopped after the call landed and before it saved its state finds the call on the next run and records it as ran without calling again. A retry calls again. This needs no workflow engine: the state file, the cursor and the key are enough. [`packages/naive/src/interfaces/tests/durable-triggers-test.ts`](../../interfaces/tests/durable-triggers-test.ts) kills the runner between the call and the save. |
| [`setup.ts`](./setup.ts) | Setup in the model's harness (EE-083). It holds the questions, and each answer is a proposal the founder confirms. `naive setup` and the MCP setup tools use it. Pointing a function at a system runs the system's sync command when the app names one ([`packages/naive/src/core/sync.ts`](../../core/sync.ts)), and the state lists those systems under `syncs`. Each docket entry carries its decision's `options` and `statement` from the record. |
| [`migrate-venture.ts`](./migrate-venture.ts) | `naive migrate` (EE-076). An agent rewrites a project as records, and each record is written through the router once a person decides. Hosted, `runAgent` refuses: the host passes its agent to `plan(from, dir, { agent })`. After `--apply`, each item's `at` is the path it was written to, a draft's path when it was held. |
| [`releases.ts`](./releases.ts) | The release rules (I-17, C-13): confirmed records frozen in, live holes named, the release card. |
| [`build-release.ts`](./build-release.ts) | `naive build`, the command line over `releases.ts`. |
| [`venture-package.ts`](./venture-package.ts) | The venture package with the idea map's routing (EE-067, EE-061): `venturePackage(dir)` passes `route()` from the idea map into `packages()` in `packages/naive/src/engine/packages.ts`, and it holds the command line for the `system/package` route. |
| [`signals.ts`](./signals.ts) | The signal pull (signal library design, build item 5), at router level because only router code may act as the signal projector (`asProjector`). The signal engine [`packages/naive/src/engine/signals.ts`](../../engine/signals.ts) reads and decides; this commits. `pull` reads the log lines each library published after the cursor (`.naive/signals.json`), finds the touched subjects (a new signal names one, a new signal withdraws one a projected record cites, or after the cursor a person or another agent wrote a record in a collection a listener reads the ids of, or a fact file a projected record cites), renders them, and diffs: a new or changed record is written through the router as the projector with `derived_from` set to the cited signal addresses and fact files, an unchanged one is verified through freshness and not rewritten, a record a projection writes once and a person now owns is kept, a proposal goes through `propose` in [`decisions.ts`](../../engine/decisions.ts) unless its id exists, and a mark through `mark` in [`stale.ts`](../../engine/stale.ts) unless it was made. Facts a predicate reads are read through the router as the projector. The cursor moves only after every write succeeded, and the projector's own provenance lines touch nothing, so a pull after a pull writes nothing. `explain` gives one signal at every listener, `replay` renders every projected record again and reports drift without writing, and `emit` writes a person's signal and its log line to the local library `raw/signals/`, refusing props that do not match the type; the same signal emitted twice is written once. The routes are `system/signals` (pull), `system/signals/replay` and `system/signals/explain`; the commands are `naive signals emit|pull|explain|replay`. A pattern with a live recipe (`<pattern>.recipe.ts`, autoresearch build plan item 9) renders through it in the sandbox instead of the plain fold: the listeners' render still runs whole, so proposals, marks and the ids other listeners read stay the same, and only the records at the recipe's pattern are the recipe's, each cited by the signals it called salient. Every recipe renders before anything is written, so a recipe that cannot be read or fails writes nothing. Beside each record it renders the pull writes `<record>.reception.json` through the venture's store, logged as the projector's (the reception route has no write action), with a new or changed record, and with an unchanged one only when what its receptions say changed. Each pull, also one with nothing new, fills hindsight in every receptions file whose as-of point plus the record type's horizon has passed, running the recipe that rendered it (live, or from the blob store) with and without each signal. `replay` renders through recipes too; `explain` does not show a recipe's receptions (not built). Withdrawing a decision a retracted signal raised is not built. |
| [`seams.ts`](./seams.ts) | Seam detectors at run time (lead agents build item 6). For each seam in [`packages/naive/src/checks/check-seams.ts`](../../checks/check-seams.ts) whose detector is in force (the venture's `governance/detectors/<id>.json`, else Naive's default), the sensor scores every record on both sides and the detector's criterion makes each call. A no call is quiet. A yes call appends a trial through `governance/detector-trial/<id>` (action `append`) and opens a decision through `decisions/<id>` (action `write`) put to the detector's `assign_to` role (`finance-lead` for tools against spend), carrying the trial in `detector_trial`; the decision id hashes the findings, so the same drift is filed once, open or settled. Each settled decision then resolves its trial: decided (acted on) is a hit, withdrawn or answered Dismiss a false alarm (signal override), by the person who settled it. An open or deferred decision resolves nothing. No model; it changes no record of either function. |
| [`recipe-search.ts`](./recipe-search.ts) | `naive recipes search <pattern>`, knob descent with no model (autoresearch build plan item 10). Coordinate descent over the knobs of the recipe at `recipes/<pattern>`: for each knob in name order it tries one step each way (`stepsOf` in [`packages/naive/src/engine/recipes/knobs.ts`](../../engine/recipes/knobs.ts)), each step the tip's source with that one value rewritten (`setKnob`), checked to read back through the sandbox as that knob alone changed, and written to the recipe route as the agent `knob-search`, so the router scores it against the tip and an agent's keep is held as a draft, which goes live only when a person accepts it with `mentura accept recipes/<pattern>` and its holdout check (build plan item 8). A keep moves the tip and the search goes to the next knob; a pass that keeps nothing takes the square root of the step factor, up to `--shrinks` times. It stops when no step is kept at the smallest step, when the plan's dev budget is spent, at `--max-writes`, or on a refusal with no verdict. A candidate the plan's log has already scored is not written again. It never supplies a score and calls no model. A list, and a string that is not a rating floor, have no step. |
| [`model-steps.ts`](./model-steps.ts) | Model steps (use model, EE-073): the payload code computes, the judgments a model still owes, and how code accepts, overrules or routes each answer. The route is `system/steps`. Hosted, `MENTURA_MODEL_CMD` is ignored and the host passes `ask` to `run`. |

## Run and test

- `node packages/naive/src/router/orchestration/triggers.ts <venture dir> --fire` runs the triggers once.
- `node packages/naive/src/router/orchestration/build-release.ts <venture dir> [--dry-run] [--json]` builds a release.
- `node packages/naive/src/router/orchestration/migrate-venture.ts --from <project> --venture <dir>` writes a migration plan.
- `node packages/naive/src/router/orchestration/venture-package.ts <venture> [--write] [--json]` prints or writes the venture package.
- `node packages/naive/src/router/orchestration/signals.ts <venture dir> pull|replay|explain <signal id>|emit <type> --props '<json>' [--now <iso>] [--json]` runs the signal library; [`packages/naive/src/interfaces/tests/signals-pull-test.ts`](../../interfaces/tests/signals-pull-test.ts) tests it end to end over two ventures, and [`packages/naive/src/interfaces/tests/recipe-render-test.ts`](../../interfaces/tests/recipe-render-test.ts) tests rendering through recipes.
- `node packages/naive/src/router/orchestration/seams.ts <venture dir> [--json]` runs the seam detectors once: resolves the trials of settled seam decisions, then calls every built seam; [`packages/naive/src/interfaces/tests/seams-test.ts`](../../interfaces/tests/seams-test.ts) tests it.
- `node packages/naive/src/router/orchestration/recipe-search.ts <venture dir> <pattern> [--factor 2] [--shrinks 2] [--max-writes 200] [--json]` runs the knob search; [`packages/naive/src/interfaces/tests/recipe-search-test.ts`](../../interfaces/tests/recipe-search-test.ts) shows a fixture venture improving with no model.
- These tests cover them: [`packages/naive/src/interfaces/tests/setup-test.ts`](../../interfaces/tests/setup-test.ts), [`packages/naive/src/interfaces/tests/model-steps-test.ts`](../../interfaces/tests/model-steps-test.ts), [`packages/naive/src/interfaces/tests/delegation-test.ts`](../../interfaces/tests/delegation-test.ts), [`packages/naive/src/engine/releases-test.ts`](../../engine/releases-test.ts), [`packages/naive/src/engine/upgrades-test.ts`](../../engine/upgrades-test.ts) (triggers) and [`packages/naive/src/engine/migrate-test.ts`](../../engine/migrate-test.ts). The tests in `schema/` start these modules as child processes and do not import them. `node test.mjs` runs all of them.

## How it connects

- Called by: [`packages/naive/src/interfaces/cli/mentura.ts`](../../interfaces/cli/mentura.ts), [`packages/naive/src/interfaces/cli/naive.ts`](../../interfaces/cli/naive.ts), [`packages/naive/src/interfaces/mcp/server.ts`](../../interfaces/mcp/server.ts), [`packages/naive/src/interfaces/dev/setup.ts`](../../interfaces/dev/setup.ts) and [`packages/naive/src/router/kit-boundary.ts`](../kit-boundary.ts). [`packages/naive/src/core/provenance.ts`](../../core/provenance.ts) starts `triggers.ts` by its path after every write. [`packages/naive/src/engine/workspace-init.ts`](../../engine/workspace-init.ts) starts `migrate-venture.ts` the same way.
- Calls: [`packages/naive/src/router/router.ts`](../router.ts), and modules in `schema/`, `packages/` and `knowledge/`. `migrate-venture.ts` reads each record type's schema with `recordPath` and `releases.ts` names it to the validator with `schemaNameOf`, both from [`packages/naive/src/records`](../../records/README.md), so neither depends on where the record types sit.

`releases.ts` checks each released record against its schema in process with `validateFile` from [`packages/naive/src/records/validate.ts`](../../records/README.md).

`durable-handoff.ts` runs a handoff as a durable Effect workflow when `naive.config.json` sets `durable.engine` to `sqlite` (EE-161, Effect runtime plan phase 11): one workflow per venture, handoff and attempt, each done-criterion an activity named for its id, the state in `<venture>/.naive/durable.sqlite` through [`node-sqlite.ts`](../../core/effect/node-sqlite.ts). A run that dies resumes without rerunning a finished criterion; the interrupted one runs again, so a criterion must be safe to repeat. The evidence and the handoff's evidence list are written through `router.ts` as the last activity. `naive handoff run <id>` picks it, else `run-handoff.ts`. The engine comes from [`durable.ts`](../../core/effect/durable.ts), so `postgres` runs on the host's `sql` hook. Not built: review criteria on this path (run-handoff.ts records them).

`recipe-search.ts` runs as a durable workflow when `durable.engine` is set (`searchDurable`, EE-161, phase 12c): the read and each experiment write are steps, so a search that dies resumes without writing a step twice and ends where a plain search ends. `search` takes a `Step` and is unchanged on the memory path.

`signals.ts` runs `naive signals pull` as a durable workflow when `durable.engine` is set (`pullDurable`, EE-161, phase 12b): the plan (render, recipe renders and the diff) is one step, and each record write, verify, receptions write, proposal, stale mark, hindsight label and the cursor move is its own, each checking first whether its write already landed, so a pull that dies resumes with the plan it made and writes nothing twice. `pull` takes a `Step` and is unchanged on the memory path.
