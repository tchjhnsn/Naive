# routes

Up: [repository](../../../../../AGENTS.md)

## What this is

The route table and the pure helpers that read it. Every route a venture has is generated here from the data model (read through [`packages/naive/src/records`](../README.md)), the layer and package manifests and `packages/naive/src/engine/need-now.json`, never written by hand (EE-030, EE-032). It moved here from `packages/naive/src/router/router.ts` in the monorepo rebuild so that `schema/` and `knowledge/` can read the route table without importing the router, which imports them. It imports only Node built-ins, [`packages/naive/src/core`](../../core/README.md) and [`packages/naive/src/records`](../README.md).

## Where things are

| Path | Holds |
|---|---|
| [`routes.ts`](./routes.ts) | `routes()`, `resolve()`, `canonical()` (a route or a glob over routes under its current name, following the aliases in `packages/naive/src/router/route-aliases.json`, so a decision that unlocks `purpose/product/*` still locks `product/kettle`), `glob()`, `files()`, `kits()`, `groups()`, `ventureDir()`, `ventures()`, `gateOf()`, `allowed()`, `repo` and `PHASES` (read as data from the phase modules, `packages/naive/src/phases/<id>/phase.json`, since the phases unit comes after records). It declares the command routes the router itself serves, such as `system/traces` (the venture's trace sessions, EE-121) and `system/signals`, `system/signals/replay` and `system/signals/explain` (the signal pull, replay and explain in [`packages/naive/src/router/orchestration/signals.ts`](../../router/orchestration/signals.ts)). The `system/decision-index` route's description names the decision queue across functions (EE-127). `identity/lean-canvas` runs the Lean Canvas, and one route per box of `packages/naive/src/functions/strategy/lean-canvas.json`, `identity/lean-canvas/<box>`, runs it with `--box <box>` (EE-155). `identity/venture-anatomy` runs the Venture Anatomy Matrix, and one route per sub-matrix of `packages/naive/src/functions/strategy/venture-anatomy.json`, `identity/venture-anatomy/<sub>`, runs it with `--sub <sub>` (EE-157). A log item route in `APPENDS` (today only `governance/detector-trial/[id]`, the detection ledger) has an `append` action, served by [`packages/naive/src/router/appends.ts`](../../router/appends.ts). A record item route in `CLAIMS` (today only `operations/handoff/[id]`) has a `claim` action, served by [`packages/naive/src/router/handoff-claim.ts`](../../router/handoff-claim.ts). A record type of a package that does not start with the package's name takes its route from `PACKAGE_ROUTE`, usually its folder (`connection` is `it/connections`, so the it function's first write route is `it/connections/[id]`; `lead-plan` is `operations/lead`, so a lead's plan is `operations/lead/<lead>` while its file is `operations/leads/<lead>.json`; `time-box` is `operations/time-box`, so a campaign or sprint is `operations/time-box/<id>` while its file is `operations/time-boxes/<id>.json`, EE-186; `meeting` is `operations/meeting`, so a meeting is `operations/meeting/<id>` while its file is `operations/meetings/<id>.json`, EE-200; `specialist` is `operations/specialist`, so a temporary specialist is `operations/specialist/<role>` while its file is `operations/specialists/<role>.json`, EE-213; `product-capability` is `product/capabilities`, beside `product/bugs`, EE-224). A record route whose type has `writer: "projection"`, `writer: "person"` or `writer: "function"` in the data model carries `writer`, which the router's gate hooks read to let only the signal projector, only a person, or only the function's agent and a person write it; a `writer: "function"` route also carries the record type's `function` (`finance/spend/[id]`, the spend register, carries `finance`, so only `finance-agent` may write it; `it/connections/[id]` carries `it`). The route `recipes/[...pattern]` (`recipe: true`, no files of its own, actions read, write, accept and monitor) ends in a catch-all segment: `resolve()` gives the rest of the route, slashes and a literal `[id]` included, as `params.pattern` (`recipes/competitors/[id]/signals`), and the router hands it to [`packages/naive/src/router/recipes.ts`](../../router/recipes.ts). A route is writable when its type is JSON with a schema, or its form is prose or markdown, and it is a collection item or a concrete file. A Markdown record type in `TEXT_ITEMS` (today only `marketing-content`) whose paths are folders of any depth (`marketing/content/**/*.mdx`) also gets a writable item route, `marketing/content/[id]`, whose id may hold slashes: `resolve()` gives `marketing/content/home/what` the id `home/what` (`deepItem`), and the router writes it to `marketing/content/home/what.mdx`. |
| `PACKAGE_ROUTE` in [`routes.ts`](./routes.ts) | The route base a record type takes when it is not its layer path. `triage` takes `raw/triage` (raw triage build item 1), so a run is `raw/triage/[id]`; `raw-dump` keeps its layer path, `purpose/raw/dump/[id]`, because `raw/dump` is the single dump of `idea-dump` `opportunity` takes `sales/opportunities`, `support-policy` takes `support/policy` and `support-case` takes `support/cases` (the sales and support packages). `market-anatomy` takes `markets` and `industry-anatomy` takes `industries` (the Venture Anatomy Matrix, EE-157), so a market is `markets/[id]`. `marketing-message` takes `marketing/message` (EE-216), so one element of a page's words is `marketing/message/[id]`, beside `marketing/sitemap` and `marketing/content`. `publish-terms` takes `marketing/publish-terms` (EE-214), the marketing function's own terms for the publishing lint. `pre-registration` takes `foundation/pre-registration`, so one is `foundation/pre-registration/[id]` while its file is `foundation/pre-registration/<id>.json` (EE-220); the router's freeze hook ([`packages/naive/src/router/pre-registration.ts`](../../router/pre-registration.ts)) refuses a write of that route that would change a registered field. `bet` takes `foundation/bets`, so one is `foundation/bets/[id]` while its file is `foundation/bets/<id>.json` (EE-221); its freeze hook ([`packages/naive/src/router/bets.ts`](../../router/bets.ts)) refuses a write that would change a frozen field of a registered bet or of a claim a registered pre-registration tests, and refuses an agent's write of a status, a probability, a resolution or the registration fields outright. |
| `ID_CHECKS` in [`routes.ts`](./routes.ts) | The checks that take one record's id after the venture folder (today only `packages/naive/src/checks/check-ready.ts`), so the `check` action of an item route names the item it is checking (EE-214). Every other check is given the venture folder alone. |
| [`commands.ts`](./commands.ts) | The command routes the function modules add (brand, the lint suites, the cache), as data. Each module in `schema/` re-exports its own list. |

A record's template is `<record>.md`, or one whose name starts `<record>-`, in its package's template dir or beside its manifest. A layer manifest keeps no templates beside it since EE-118 step 7, so its templates are looked up in the function modules' `templates/` folders, in the order `packages/naive/src/functions/departments.json` lists the functions.

`defaultWorkspace()` is `MENTURA_WORKSPACE`, else the current directory. The framework never defaults to a folder of its own. A venture's decision rights start from the template's, `packages/naive/template/governance/decision-rights.json`, tightened by the venture's own file. A record type's venture-relative paths come from `venturePaths` in [`packages/naive/src/records`](../README.md).

The command routes `routes.ts` adds itself include `system/phase-gate` (EE-156), which runs `packages/naive/src/engine/phase-gate.ts`: each item of the current phase gate on its evidence ladder against the venture's policy, and `system/phase-gate/calibrate` (EE-157), which runs `packages/naive/src/engine/gate-calibration.ts`: the gate's thresholds derived from the venture's market and industry. It is a `.ts` command route, run by Node's type stripping like `system/signals`. `operations/activity-briefing` and one route per function, `operations/activity-briefing/<function>`, run `packages/naive/src/engine/activity-briefing.ts` (EE-180): the briefing a person reads, derived on each read, with nothing written. `purpose/validation/problems` and `purpose/validation/problems/rank` run `packages/naive/src/engine/problems.ts` (EE-219): the customer problem tree with its narrower cases and causes, and the ranking computed from the evidence coded on the venture's interviews. Both read only.

`packages/naive/src/router/router.ts` re-exports everything in `routes.ts`, so code that imports the route table from the router keeps working. New code below the router imports `packages/naive/src/records/routes/routes.ts`.

## Run and test

- `node packages/naive/src/interfaces/test.ts` covers the route table through the router, and `node test.mjs` runs it.
- `node scripts/dependency-rules.ts --graph` shows that `packages` imports no other unit.

## How it connects

- Called by: [`packages/naive/src/router/router.ts`](../../router/router.ts), and in `schema/` the decision matrix, freshness, staleness, upgrades and the config, team, where-used and docs checks; [`packages/naive/src/store/connectors/catalog.ts`](../../store/connectors/catalog.ts); the site's data scripts.
- Calls: [`packages/naive/src/core/action-scope.ts`](../../core/action-scope.ts) to build the table once per action, [`packages/naive/src/core/venture-paths.ts`](../../core/venture-paths.ts), and [`packages/naive/src/records/index.ts`](../index.ts) for the data model.
