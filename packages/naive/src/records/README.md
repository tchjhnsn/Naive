# records

Up: [repository](../../../../AGENTS.md)

## What this is

The resolver for the record types: the framework's JSON Schema files (`<name>.schema.json`) and the data model (`data-model.json`). Every piece of code that reads one of them asks this module where it is, instead of building the path from the folder name `schema`. Today the files still sit in [`schema/`](../engine/README.md). The monorepo rebuild (step 5a; its design, `MONOREPO_RECORDS_PACKAGE_2026-11-05.md`, is in pull request #243) moves them here in a later pull request, and because every loader goes through this module, that move changes the folder here instead of every loader. It imports nothing in the repository, and `node scripts/dependency-rules.ts` fails if it does.

- `raw-source.schema.json` is one source at `raw/sources/<id>/source.json` (EE-070, EE-192). `fetched_at`, `url`, `archive_of`, `http_status` and `self_reported` are null when not known. `sha256` is the text, written by the router. A record from before EE-192 may omit the new fields.
- `venture.schema.json` names three layouts: flat, structured (EE-086) and src (EE-118 step 8, package folders under `src/<function>/` beside `public/`). `types/records.d.ts` is generated from the schemas.
- `evidence.schema.json` is one run of a check or eval (`evidence/results/<id>.json`). A test of a physical thing names the unit tested (`subject.article`, a serial), the `conditions` it ran under, and each result's `measured` values, each a quantity, a number, a UCUM unit code and an optional limit; `check-execution.mjs` refuses a result that passes outside its limit. Units are not converted or checked against UCUM.
- `trace-span.schema.json` is one line of a venture's `traces/<session>.jsonl`, a span after the OpenTelemetry GenAI conventions, hash-chained (EE-121); `provenance-entry.schema.json` names the span a write ran in, and `naive-config.schema.json` turns traces on with `traces`.
- `provenance-entry.schema.json` also carries `rechained_from` (EE-177, offline sync): a line a working copy wrote offline that a push wrote again on top of the business store's chain keeps its own time, entity, activity, agent and sha256, takes `prev` and `hash` from the store's chain, and names in this block the `hash` and `prev` it had in the working copy's log and the `working_copy` it came from. `packages/naive/src/core/rechain.ts` writes the block and `packages/naive/src/checks/check-provenance.ts` refuses one that does not hold.
- `naive-config.schema.json` holds `durable.engine` (memory, sqlite or postgres; EE-161), read by `packages/naive/src/core/effect/durable.ts`. Each entry of `publish_lint.marks` is a name or an object with `name`, `private` (never public) and `why` (EE-214).
- `publish-terms.schema.json` is the marketing function's own publishing terms at `marketing/publish-terms.json` (EE-214): `marks`, each a `name` with optional `private`, `why` and `until`. It takes no severity and no waiver, which stay in `naive.config.json`, so the function that owns the words can only tighten the gate.
- `marketing-sitemap.schema.json` gives a section `draft_copy` (`text`, `status` of draft, ready or published, `sources`, `by`, `at`) and takes no other field, so copy lives in a field the publishing lint reads and an invented one is refused by name (EE-214).
- `naive-config.schema.json` holds `loops` (EE-183): `mode`, `functions` and `workflows`, each manual, ask or auto, and `set_by`, read by `packages/naive/src/engine/loop.ts`.
- Time boxes (EE-186). `time-box.schema.json` is one campaign or sprint at `operations/time-boxes/<id>.json` (route `operations/time-box/[id]`), in the operations layer with function null, data transactional and writer person: its kind, title, goal, `starts`, `ends`, status (active, closed or cancelled), the `functions` or `workflows` it covers (at least one of the two), and an optional `loop_mode`, which requires `set_by`. It is open while active, from `starts` until `ends`. A write whose end is not after its start is refused. `function-workflow.schema.json` gives a trigger an optional `during`, campaign or sprint: the workflow is due only while such a time box is open that covers it.
- Meetings (EE-200). `meeting.schema.json` is one meeting at `operations/meetings/<id>.json` (route `operations/meeting/[id]`), in the operations layer with function null, data transactional and writer any: a `goal` and `outcome_expected` stated before it opens, `called_by`, `attendees` (people and agents), an `agenda` worked in order whose items may name a `step` of the `workflow` it walks, each item pending, done, skipped or handed-off, then `minutes`, the `outcome`, per-attendee `takeaways` and the `recording`. Status planned, open, closed or abandoned; an open meeting has `opened_at`, and a closed one has its outcome, `closed_at` and no pending item. A command that runs a meeting is not built in Naive.
- `naive-config.schema.json` holds `sync.host`, the business store `naive sync link` signs in to when `--host` is not passed (EE-178), read by `packages/naive/src/engine/sync.ts`. No token lives there: it goes to the operating system's keychain. The data model's `files` give `instance/**/.naive/sync.json` the kind derived, because one working copy's sync state belongs to that copy alone and a full pull rebuilds it.
- `naive-config.schema.json` holds `phase_gates` (EE-156): `preset` (lenient, standard or strict), `enforce` (lifecycle advance refuses a fail-closed shortfall), `items` (per phase and gate item, `min` and `boundary`), `count_levels` (the interview counts that reach low, moderate and high, in place of the policy file's) and `staleness_months` (how old evidence may be before it drops a level, default 18), read by `packages/naive/src/engine/phase-gate.ts`. `packages/naive/src/engine/gate-calibration.ts` proposes the last two from the venture's market and industry (EE-157). `gate-calibration.schema.json` is the shape of its rules file, `packages/naive/src/phases/gate-calibration.json`. `validation-plan.schema.json` is a venture's `validation/plan.json`, the assumptions each with its test, pass result and date, which the gate's coverage item reads.
- `detector.schema.json` is one yes or no call a venture makes on evidence (`governance/detectors/<id>.json`), after signal detection theory: its question, impact tier, where its signals come from (`evidence.sources`: a source of the venture and the route of the records read there), sensor, criterion, the costs of the four outcomes and the base rate. The tier sets the default costs: at low a miss costs the same as a false alarm, at costly three times as much, and a one_way_door detector has no costs and the criterion `route: person`, so every call goes to a person. `detector-trial.schema.json` is one line of the detection ledger beside it (`<id>.trials.jsonl`): a trial (score, criterion in force, call) or a resolution (hit, miss, false-alarm or correct-rejection, and who settled it), hash-chained like the provenance log. `evidence.scale.yes_when` is `above` (the default: a score at or above the yes line is yes) or `below` (a score strictly below it is yes, as the gate holds a write), and a trial copies it into its criterion; scores are never inverted. A line Naive ships, chosen by hand in Naive and not by a person of the venture, is `set_by: "default"`; those defaults are in `packages/naive/template/governance/detectors/`. The example is `examples/software/ventures/relay/governance/detectors/`. An optional `assign_to` names the role a yes call's decision is put to, as a seam detector names the lead whose portfolio spans the seam; `decision-record.schema.json` carries it as `assigned_to`, and the trial the decision settles as `detector_trial` (lead agents build item 6).
- `decision-record.schema.json` carries `duplicate_of`, `withdrawn_by` and `withdrawn_at` on a decision a person withdrew, `duplicate_of` naming the decision that asks the same question (EE-185).
- `decision-record.schema.json` carries `candidates` and `reopened` (EE-211). A candidate is one idea for the record the decision decides: an id, a label, a `why`, `proposed_by` (a person or an agent), `evidence`, and either `body`, the whole proposed record, or `patch`, the fields it proposes, never both; a candidate with neither is an option with provenance whose label merges as the answer. Any number coexist while the decision is open, so an undecided record holds several ideas at once, which a record type with no options of its own, a goal or a requirement, could not do before. A withdrawn candidate keeps `withdrawn_by`, `withdrawn_at` and `withdrawn_why` and is never removed. `reopened` is one entry per reopen: the version, the answer it held, who, when, in which phase, why, and `override` when the person reopened it past Validation or reopened a one-way door. The rules are in `packages/naive/src/engine/decision-candidates.ts` and the doors in `packages/naive/src/engine/decisions.ts`.
- `goal.schema.json` is a durable record (EE-210), like the decision ledger: `status` (proposed, active, met, missed, dropped or superseded, defaulting to proposed so a goal written before the ledger stays valid) with `status_by` and `status_at`, the goal it serves (`parent`), the goals it replaces (`supersedes`, `superseded_by`), a `due` date, where it came from (`sources`) and the `result` it was settled on. Three invariants are in the schema: a superseded goal names its successor and only a superseded goal has one, and a met or missed goal has a result. `packages/naive/src/engine/goals.ts` holds the lifecycle and the write rule the router applies, and `packages/naive/src/checks/check-goals.ts` the links between goals and the requirements that derive from them.
- `decision-record.schema.json` carries `sync_conflict` on a decision offline sync files (EE-175): the record file, the path, the base, local and store values and who wrote each. A person answers `store`, `local` or a value of their own as JSON, and merging the decision writes it at the path (`packages/naive/src/engine/sync-apply.ts`).
- `capability-cluster.schema.json` and `connection.schema.json` (lead agents, build plan item 7, docs/design/LEAD_AGENTS_2026-11-08.md). The catalog at `packages/naive/src/functions/it/capability-clusters.json` lists the whole-venture monorepo thesis's six capability clusters, the functions (`departments.json` ids) that depend on each and the gap kinds that justify an outside tool (regulated authority, a network or money rail, a runtime, a UI preference); every object allows only its listed properties, so a vendor field fails the schema. A `connection` (`it/connections/<id>.json`, function it, owned by the it package) is one outside system a venture connects under the thesis's eight-point contract: `authoritative_for` (source map rules named by record type and attribute, since rules carry no id), `sync` (default tool to repo, references only), `access` reads and writes with scopes, signed `events`, `external_id` with provenance and last-synced time, `actions` each naming its approval class, `idempotency` with retries and reconciliation, `exit`, and `failure` (what goes stale, blocks or degrades). It optionally names its `integration`. `packages/naive/src/checks/check-connections.ts` checks what the schema cannot.
- `tool-catalog.schema.json` (EE-163). The catalog at `packages/naive/src/functions/tools.json` is a taxonomy of function (a `departments.json` id), APQC level 2 process group and tool. A tool names the record types it reads and writes, which must be in the data model, and the ones it proposes, which must not be; a tool with function null is universal. It names no vendor. Its process groups carry the hierarchy ids, names and element ids of APQC's PCF 8.0 (EE-166). `packages/naive/src/checks/check-tools.ts` checks it across files, and `packages/naive/src/checks/check-pcf.ts` fails when a process group differs from `pcf.json`.
- `language-rubric.schema.json` (EE-189). The rubric at `packages/naive/src/functions/it/language-rubric.json` holds criteria for judging which programming language fits a system, each with a question, why, the ISO/IEC 25010:2023 characteristics it serves, described levels on a 0 to 4 scale, a default weight that is an unvalidated prior, an optional `gate` (a 0 rules a candidate out) and reference ids as `sources`, and worked examples: a system, its target, optional `weights` and `must` for that system, candidates scored with a reason for each score, the person's choice and the decisions that record it. `packages/naive/src/checks/check-language-rubric.ts` checks what the schema cannot (weights sum to 1, sources and decisions resolve).
- `visibility-rubric.schema.json` (EE-222). The rubric at `packages/naive/src/functions/it/visibility-rubric.json` holds criteria for judging how far a tool gives the system visibility of an activity and how far the venture owns the record, each with a question, why, the ISO/IEC 25010:2023 characteristics it serves, described levels on a 0 to 4 scale, a default weight that is an unvalidated prior, reference ids as `sources`, an optional `gate` (a 0 rules a candidate out) and an optional `blind_spot` (a 0 means the tool records nothing, which is flagged and never rules a candidate out). It also holds the `channels` an activity is performed on, each with clauses on the words of its statement as the activity catalog's `kinds` hold them (one channel is the `default` and names none), and the `tool_kinds` that capture each, with prior scores and a reason per score, named as kinds and never as vendors. Worked examples name an activity, its channel, the candidates, optional `weights` and `must`, the person's choice and the decisions that record it. A venture's own `weights` and `must` live under `visibility` in `naive-config.schema.json`. `packages/naive/src/checks/check-visibility-rubric.ts` checks what the schema cannot.
- `activity-catalog.schema.json` (EE-164). The catalog at `packages/naive/src/functions/activities.json` lists the scales an activity may be scored on and the activities: each an O*NET task statement under an APQC level 2 process group, optionally a level 3 process from `packages/naive/src/functions/pcf.json`, with a scope that is cross-industry or one NAICS code, an optional source reference, and optional ratings, which require `rated` (who, when, on what basis). `packages/naive/src/checks/check-activities.ts` checks it across files. `proposal_rules` (EE-169) are optional: each rule is `{id, when, asks, basis}`, where `when` lists lines on scales (`{scale, at_least?, at_most?}`), `asks` is the question for a person and `basis` says why the lines sit there. `naive-config.schema.json` has `activity_proposals.rules`, a venture's own lines per proposal rule: `off`, or `{ when }` in the shape of the catalog's lines (EE-170). `activity-assignments.schema.json` is the venture's `operations/activity-assignments.json`: per activity id, `performer` (agent or person) and `approval` (person or none), written by merging a decided activity proposal (EE-172). A proposal rule's optional `sets` in `activity-catalog.schema.json` names which of the two its answer sets. A function agent's brief for the venture carries the assignments of its function's activities (EE-173, `packages/naive/src/engine/agents/assignments.ts`). An assignment's key is a catalog activity or the hierarchy id of an APQC level 4 activity such as `3.5.1.6` (EE-176), which is what the shipped workflow steps name; a person writes those through `operations/activity-assignments`, and no rule proposes them. The catalog's `kinds` (EE-179) say which activities a person performs by default: each kind is `{id, performer, when, basis}`, where `when` is a list of clauses of `verbs`, `terms` or both, read against the first word and the later words of an activity's statement. The record holds no default: an activity the venture has not assigned takes its kind's.
- `function-workflow.schema.json`: a step with `consider` is one to consider, not one the workflow requires, and says `why` and optionally `when` (EE-181).
- `function-workflow.schema.json`: every workflow has a `goal`, what one run must make true in one sentence, and `measures`, the telos measure kinds the run moves, which `packages/naive/src/checks/check-functions.ts` holds to a subset of its function's in `function.json` (EE-215). A trigger's `cadence` is required for `schedule` and refused elsewhere, and its `route` is required for `event` and refused elsewhere, so neither kind can be written in a shape that is never due.
- `function-workflow.schema.json`: a step may name the `activity` it performs, the hierarchy id of an APQC level 4 activity in `packages/naive/src/functions/pcf.json` or the id of an activity in `packages/naive/src/functions/activities.json` (EE-168). `packages/naive/src/checks/check-functions.ts` checks it sits under the function's APQC category.
- `department-catalog.schema.json` (EE-047, EE-199). `packages/naive/src/functions/departments.json` lists the 13 functions. Each `apqc` entry has the category's hierarchy id, its PCF 8.0 name and its element id from `pcf.json`.
- `pcf.schema.json` (EE-165). `packages/naive/src/functions/pcf.json` is APQC's Process Classification Framework: its version, edition (cross-industry only), month published, a reference source, APQC's required attribution verbatim, and every element of levels 1 to 5 as `{id, name, pcf, level}`. A category's id ends in `.0`; below it each part counts from 1. Element ids (`pcf`) are not required to be unique, because APQC repeats a few. `scripts/import-pcf.ts` writes the elements and `packages/naive/src/checks/check-pcf.ts` checks them across elements.
- `element-owners.schema.json` (EE-187) is the venture's `operations/element-owners.json`: per element of APQC's framework, by its hierarchy id at any level (`3.0`, `3.5`, `3.5.1.6`), the accountable owner, either `{ role }` (a role template id or `<function>-agent`) or `{ person }` (a name), never both. An element with no entry takes its parent's owner, and `packages/naive/src/engine/element-owners.ts` resolves the rest.
- `lean-canvas.schema.json` is the Lean Canvas definition (EE-155), `packages/naive/src/functions/strategy/lean-canvas.json`: nine boxes, each naming the record type and attribute it references; `venture.schema.json` core gains `unfair_advantage`, which the canvas's unfair-advantage box reads.
- `venture-anatomy.schema.json` is the Venture Anatomy Matrix definition (EE-157), `packages/naive/src/functions/strategy/venture-anatomy.json`: the coverage items (Regulation S-K), the sub-matrices (record types, owner, items covered, phase expected, nesting) and the viewpoints. `anatomy-cell.schema.json` is a part, not a record type: the one cell shape (status known, estimated or unknown, never null; value; evidence; `valid_from` and `valid_to`, application time) that `market-anatomy.schema.json` (`markets/<id>.json`, route `markets/[id]`, function marketing-and-sales) and `industry-anatomy.schema.json` (`industries/<id>.json`, route `industries/[id]`, function strategy) use for every cell. The purpose layer owns all three record types. The examples are the relay venture's `markets/primary.json` and `industries/naics-513210.json`.
- `phase-module.schema.json` is a lifecycle phase as a module (EE-126), `packages/naive/src/phases/<id>/phase.json`: its step, question, stage gate (name, the questions it asks and the exit evidence it requires, each naming the record type it is kept in), the function workflows active in it and the weights per function. `lifecycle-playbook.schema.json` makes a playbook's `gate` optional: a playbook names one only when it renames the phase module's. `packages/naive/src/checks/check-phases.ts` checks what the schema cannot.
- `phase-gate-policies.schema.json` is how strict each phase gate is (EE-156), `packages/naive/src/phases/gate-policies.json`: per phase, the gate items (what each asks, the record type that proves it or null for a person's act, how its strength is measured: count, grade, coverage or authority, and the fields it requires) and named presets giving each item a minimum evidence level (very low to high) and a boundary, fail-closed or fail-open. `packages/naive/src/engine/generators/phase-gate-policies.ts` checks what the schema cannot (known record types, presets that cover every item) and scores a preset's strictness. `validation-plan.schema.json` is a venture's `validation/plan.json`, owned by the validation package: the open assumptions, each with the gate item it bears on, its test, the result that passes and a date.
- `handoff.schema.json` done criteria have an optional `runs`, `bash` (the default) or `effect` (EE-161): an effect criterion's `check` is a venture program run on the venture runtime by `run-handoff.ts`.
- `handoff.schema.json` has two optional fields for the handoff claim (lead agents, build plan item 5, docs/design/LEAD_AGENTS_2026-11-08.md): `requested_by`, the lead role or person that wrote the handoff and verifies it, and `verification` (`by`, `at`, `outcome` accepted or rework, `reason`), the requester's verdict on done work. `claimed_by` is set by the router's `claim` action. A handoff without them is unchanged.
- `competitor.schema.json`: besides the name, a competitor record may hold `kind` (competitor, or an alternative the customer uses in its place), `basis` (interview, public-source or guess), `offering`, `for`, `price`, `does`, `does_not`, `sources` with the date each was read, and `next_move`. All are optional. `competitor-signals.schema.json` gains `prices` and `hiring`, folded from the `price-change` and `job-posting` signal types.
- The signal library's record types (build item 2 of the signal library design , everything-ecosystem docs/design/SIGNAL_LIBRARY_2026-11-06.md). `signal-type.schema.json` is a component: id, semver version, props (a JSON Schema), the parts it composes, `projects` (folds into record routes from six fixed reducers: set, first, max, min, union, and append with unique_by; `once` creates a person's master record only when it is missing; `subject_field` names the record field that holds the subject), `freshness.max_age` and worked cases. `signal.schema.json` is an element: CloudEvents names with `producer` and `props`, a valid `time` and a transaction time `observed`, an Admiralty `rating` (reliability A to F, credibility 1 to 6), `cites`, and at most one of `retracts` or `supersedes`; its `id` is the first 24 hex characters of the sha256 of the canonical JSON of every other field (`packages/naive/src/core/signal-id.ts`). `signal-library.schema.json` is a library's `library.json` (contract `naive-signal-library@1`), and `signal-log.schema.json` one line of its day index `log/<type>/<yyyy-mm-dd>.jsonl`. `listener.schema.json` is a part, not a file: `naive-config.schema.json` holds `listeners` (each naming its consumer) and `listeners_off`, `frame.schema.json` holds `listens` (the frame is the consumer, and a frame's listener never projects), and `packages/naive/src/checks/check-data-model.ts` checks a package manifest's `listeners`. A listener hears a type range, carries a criterion (a worst rating, producer prefixes and predicates whose operand is a literal, `{ "read": "<file>#<field>" }` or `{ "ids": "<collection>" }`) and then projects, proposes or revalidates; only edge listeners (propose, revalidate) may carry `max_age`. `knowledge-sources.schema.json` gives a source `carries`: records or signals, and `confirmed_by` (a person and a time), without which a signal library whose connector is not the filesystem is not read. `competitor.schema.json` is a person's master record (`competitors/<id>.json`) and `competitor-signals.schema.json` what signals say about it (`competitors/<id>/signals.json`), which the data model marks `writer: projection`. Both are owned by the competitors package (`packages/naive/library/packages/competitors/`, build item 6), not the purpose layer. The examples are in `examples/signals/`. The router enforces `writer: projection` (build item 4): only the signal projector writes such a record, and everyone else, a person included, is refused with the hint to emit a superseding signal (`writerRule` in `packages/naive/src/engine/gate.ts`). `packages/naive/src/engine/signals/render.ts` renders signals into records as pure functions, `packages/naive/src/engine/signals.ts` reads libraries and merges listeners, and `naive signals pull` (`packages/naive/src/router/orchestration/signals.ts`) commits as the projector. `packages/naive/src/checks/check-signals.ts` checks signal libraries, signal types (each worked case rendered) and listeners beyond what these schemas can say.
- The autoresearch record types (build plan item 3 of the autoresearch design, everything-ecosystem docs/design/AUTORESEARCH_RECORDS_2026-11-06.md). A recipe is TypeScript source at `<pattern>.recipe.ts` beside the records it makes, so its record type has the new form `typescript`: `recipe.schema.json` governs only what the module exports (`hears` and `knobs`, as the sandbox's `recipeExports` reads them), and `validate.ts` never reads the file. A path segment `[id]` in a pattern is literal. `eval-plan.schema.json` is `<pattern>.plan.json`: the as-of points of the training, dev and holdout windows, `horizon`, `gap`, `read_cut`, `weights` (uniform or cited), `min_gain`, an optional block `bootstrap`, `budgets` for dev evaluations and holdout checks, compute `limits`, a person as `made_by`, and `sha`, the sha256 of the canonical JSON of every other field. `experiment.schema.json` is one line of `<pattern>.experiments.jsonl`, hash-chained like provenance: an experiment (candidate, base and plan sha, verdict keep, discard or fail, the dev score with its standard error and margin, the actor and the trace span) or a person's holdout check (pass or fail, and whether accepted over it, which `mentura accept recipes/<pattern>` writes, build plan item 8). `reception.schema.json` is `<record>.reception.json`: per heard signal, salient (with the fields it fed) or noise (with every reason it failed), its valid, transaction and withdrawal times, the bitemporal factors (lag, age, the producer's confirmed and withdrawn shares, uptake), an optional hindsight label (helpful, inert or harmful, with the recipe's sha), and on a noise reception only an optional `probe` (its rate: the signal was surfaced anyway, so a recipe that would surface it can be scored on its outcome, weighted by one over the rate; `research.probe_rate` in `naive-config.schema.json` sets the share, 0 by default, and `packages/naive/src/engine/recipes/probes.ts` draws it); the data model marks it `writer: projection`. A projected record type may carry `settles` (`data-model.schema.json`): horizon, cadence, a loss per field from exact, set-jaccard and abs-scaled, forecast fields each resolved by signal type ranges or a person's decision within a window, and minimum rows per window; `competitor-signals` settles its funding, first and last seen and forecasts `p_raise_90d`. The data model's `files` give `_eval/**` (a frozen eval set, at `<venture>/_eval/<sha>/`) the kind record: an eval set cannot be rebuilt, so a host commits it, and it never changes, so a base check can only pass. The examples sit beside the signal examples in `examples/signals/`, and `packages/naive/src/checks/check-recipes.ts` checks that they agree across files. `naive recipes plan` writes a plan and its eval set (`engine/recipes/eval-set.ts`), `naive recipes init` a person's starter recipe (`engine/recipes/starter.ts`), and the signal pull writes receptions beside each record a live recipe renders, as the projector, and fills their hindsight (`engine/recipes/render.ts`, build plan item 9). Nothing writes experiment lines in a venture yet, and programs are a person's (`writer: person`); the gate rule that keeps plans a person's is a later build item, and receptions are the projector's (`writer: projection`).

- `schemaFile` and `readSchema` take a name, `venture` or `venture.schema.json`, never a path.
- `recordPath` maps a stored repository path, as the data model and the package manifests name a schema (`packages/naive/src/records/venture.schema.json`), to the absolute file. A stored path under another folder, such as an app's `app/schemas/claim.schema.json`, resolves from the repository root. The prefixes it reads are listed in `PREFIXES`, so the move can accept `packages/naive/src/records/` and keep `schema/` for one release.
- Every record type in `data-model.json` names its owning `function`, an id in `packages/naive/src/functions/departments.json`, or null for a type several functions share or none owns (workspace records, provenance, decisions, signals, recipes and the rest of the framework's plumbing). `data-model.schema.json` requires it and lists the ids, and `node packages/naive/src/checks/check-data-model.ts` checks that list against the catalog and each record type against `PACKAGE_FUNCTION` in `packages/naive/src/core/venture-paths.ts` and its owning package. `PACKAGE_FUNCTION` stays the map the src layout reads, because core sits below records and cannot read the data model; the check keeps the two in agreement. An app's records in `naive.data-model.json` name a function too.
- Every workspace and venture record type in `data-model.json` names `data` (EE-184), what its records are to the business in data management's terms: `master` (a lasting fact kept as one current record, such as a customer or the goals), `reference` (a list or setting other records are read against, such as the glossary), `transactional` (one event or piece of work at a time, such as a support case, a handoff or a signal) or `derived` (computed from other records). `dataOf(recordType)` reads it. Of the 119 such types, 68 are master, 6 reference, 37 transactional and 8 derived. Nothing but `check-data-model.ts` reads it yet.
- `venturePaths(record)` gives a venture-level record type's paths relative to a venture folder. In `data-model.json` those paths carry the prefix `VENTURE_PREFIX` (`instance/**/`), the name the data model has always used for a workspace. It names no folder Naive reads, so code asks `venturePaths` instead of slicing the prefix.
- `pathKind(logicalPath, model)` says what kind of file sits at a logical path in a venture, so a host that commits a working copy knows what to do with it (hosted working copy design, section 2). A `record` is written whole through the store. A `log` is append-only, so a commit may only add lines at the end. A `derived` file is a cache Naive rebuilds, which a host may keep or drop. The kind comes from the matching record type's `kind` in `data-model.json` (default `record`), or from the data model's `files` entries, which name the venture files no record type covers: READMEs, briefs and charters in prose, and Naive's own files under `.naive/`. It returns null when nothing names the path, and throws when two matches disagree. A host passes the model it holds, and the patterns are compiled once per model. Today's logs are `provenance.jsonl`, `traces/<session>.jsonl`, `knowledge/freshness.jsonl`, `.naive/telemetry.jsonl`, `.naive/decision-index-history.jsonl`, `.naive/trigger-errors.jsonl`, `.naive/lint-findings.jsonl` and `.naive/events.jsonl`. The blob store `.naive/blobs/**` is a record kind: a blob never changes and an as-of read cannot rebuild it. The derived files are `.naive/decision-index.json` and everything under `.naive/cache/`, `.naive/types/`, `.naive/upgrade/` and `.naive/publish/`. `node packages/naive/src/checks/check-data-model.ts` fails when a file in an example venture has no kind.
- `readDataModel` appends an app's own record types. An app that uses Naive, such as Mentura, keeps its record types out of Naive's data model and lists them in `naive.data-model.json` at the root of the repository being checked: `{ "records": [...], "ignore": [...], "files": [...] }`, each entry shaped as in `data-model.json`. Anything else in that file is refused. Every check that reads the data model then checks the app's records like Naive's. Naive itself has no such file. The docs site's JSON under `site/` (its configuration, lockfile, frozen facts and gate lists) is in `data-model.json`'s `ignore`: the site is an app inside this repository, not records. The same list ignores `packages/naive/founder-templates/**/*.json`, `packages/naive/exemplars/**/*.json` and `packages/naive/evals/**/*.json` (EE-198). Those files are public templates, synthetic exemplars and eval files, not venture records.
- `schemaNameOf` turns a stored path into the name `node packages/naive/src/records/validate.ts --schema` takes.
- `recordsIn(root)` gives the same functions for another copy of the repository, such as a test's temp copy (the `EE_ROOT` pattern of `packages/naive/src/checks/check-data-model.ts`).

It is `.mjs`, like [`packages/naive/src/core`](../core/README.md), until its unit moves to TypeScript; the package ships compiled JavaScript (EE-159), so nothing holds it there. Its test is TypeScript.

`node packages/naive/src/records/validate.ts` validates records in JavaScript, with no Python and no dependency. It takes `--schema`, `--def` and `--file`. It covers the JSON Schema 2020-12 keywords these schemas use and exits 2 on a keyword it does not know. Of the formats it checks only `date`, as Python's jsonschema does without optional packages. `node packages/naive/src/records/validate-test.ts` checks that it and jsonschema give the same verdict and the same failing paths on every record and on mutants of each; it runs where python3 with jsonschema is installed (CI has it) and says it skipped otherwise. Every runtime check calls it in process through `validateFile(schema, file)` or `validateValue(schema, value)`, which return what the command would (status 0 valid, 1 invalid with one `path: message` line each, 2 could not check), so the router, the engine, the CLI and the ontology gate run with no Python. `useValidator(v)` swaps in another `Validator`, for a host with schemas of its own or a test that needs a checker that cannot run.

`record-validator.ts` is the same validator for Effect code (EE-161, phase 6). `RecordValidator` is a `Context.Reference`, so an Effect that asks for it needs no layer: its default checks through `validateValue` (so `useValidator` applies), and `RecordValidatorOver(validator)` is a layer over another registry. `validate(schema, value)` fails with `SchemaInvalid` (the validator's lines) or `CannotRun` (the checker could not run, which a caller must not record as a reject). `decodeRecord<T>(schema, value)` gives the value back typed as `T`, its generated type in `types/records.d.ts`. `recordView<T>(schema)` is an Effect Schema for one record type, built with `Schema.declareConstructor`, whose check is this validator and whose issue message is its lines. Effect's own JSON Schema import is not used, because it rejects the cross-file `$ref`, `if`, `dependentRequired` and `contains` these schemas use. No caller is moved onto it yet (not built; the router's writes move in phase 8). `node packages/naive/src/records/record-validator-test.ts` decodes every JSON record in the example ventures through its view and `decodeRecord`, and checks a broken record, an unknown schema and another registry.

## Run and test

- `node packages/naive/src/checks/check-record-paths.ts` fails when code outside this module builds a schema or data-model path from the folder name (`join(root, "schema", name)`, a path literal such as `"packages/naive/src/records/data-model.json"`, a concatenation, a stored path read by its prefix, or a Python `root / "schema"`). Its allowlist names each exception with a reason.
- `node packages/naive/src/checks/check-record-paths-test.ts` checks that every schema resolves by name and by stored path and that every schema the data model names exists, and breaks the check on copies.
- `node test.ts` runs both.
