# records

## What this is

The resolver for the record types: the framework's JSON Schema files (`<name>.schema.json`) and the data model (`data-model.json`). Every piece of code that reads one of them asks this module where it is, instead of building the path from the folder name `schema`. Today the files still sit in [`schema/`](../engine/README.md). The monorepo rebuild (step 5a; its design, `MONOREPO_RECORDS_PACKAGE_2026-11-05.md`, is in pull request #243) moves them here in a later pull request, and because every loader goes through this module, that move changes the folder here instead of every loader. It imports nothing in the repository, and `node scripts/dependency-rules.ts` fails if it does.

## Where things are

| Path | Holds |
|---|---|
| [`index.mjs`](./index.mjs) | `RECORDS` (the absolute folder that holds the record types, computed from the module's own place), `schemaFile(name)`, `dataModelFile()`, `readSchema(name)`, `readDataModel()`, `recordPath(stored)`, `listSchemas()`, `schemaNameOf(stored)`, `venturePaths(record)`, `recordsIn(root)`, `globRegExp(pattern)`, `pathKind(logicalPath, model)` with `KINDS`, and `APP_DATA_MODEL` with `mergeAppDataModel`. |
| [`layers/`](./layers/) | Each layer's manifest (`layers/<layer>/layer.json`), its tooling list (`tooling/integrations.json`) and its references (`references/references.json`). They moved here from the layer folders at the repository root in EE-118 step 7, when the skills and templates went to the function modules in [`../functions/`](../functions/README.md). `layer.json` beside this README is the system layer's manifest. |

- `venture.schema.json` names three layouts: flat, structured (EE-086) and src (EE-118 step 8, package folders under `src/<function>/` beside `public/`). `types/records.d.ts` is generated from the schemas.
- `trace-span.schema.json` is one line of a venture's `traces/<session>.jsonl`, a span after the OpenTelemetry GenAI conventions, hash-chained (EE-121); `provenance-entry.schema.json` names the span a write ran in, and `naive-config.schema.json` turns traces on with `traces`.
- `detector.schema.json` is one yes or no call a venture makes on evidence (`governance/detectors/<id>.json`), after signal detection theory: its question, impact tier, where its signals come from (`evidence.sources`: a source of the venture and the route of the records read there), sensor, criterion, the costs of the four outcomes and the base rate. The tier sets the default costs: at low a miss costs the same as a false alarm, at costly three times as much, and a one_way_door detector has no costs and the criterion `route: person`, so every call goes to a person. `detector-trial.schema.json` is one line of the detection ledger beside it (`<id>.trials.jsonl`): a trial (score, criterion in force, call) or a resolution (hit, miss, false-alarm or correct-rejection, and who settled it), hash-chained like the provenance log. `evidence.scale.yes_when` is `above` (the default: a score at or above the yes line is yes) or `below` (a score strictly below it is yes, as the gate holds a write), and a trial copies it into its criterion; scores are never inverted. A line Naive ships, chosen by hand in Naive and not by a person of the venture, is `set_by: "default"`; those defaults are in `packages/naive/template/governance/detectors/`. The example is `examples/software/ventures/relay/governance/detectors/`.
- The signal library's record types (build item 2 of the signal library design , everything-ecosystem docs/design/SIGNAL_LIBRARY_2026-11-06.md). `signal-type.schema.json` is a component: id, semver version, props (a JSON Schema), the parts it composes, `projects` (folds into record routes from six fixed reducers: set, first, max, min, union, and append with unique_by; `once` creates a person's master record only when it is missing), `freshness.max_age` and worked cases. `signal.schema.json` is an element: CloudEvents names with `producer` and `props`, a valid `time` and a transaction time `observed`, an Admiralty `rating` (reliability A to F, credibility 1 to 6), `cites`, and at most one of `retracts` or `supersedes`; its `id` is the first 24 hex characters of the sha256 of the canonical JSON of every other field (`packages/naive/src/core/signal-id.ts`). `signal-library.schema.json` is a library's `library.json` (contract `naive-signal-library@1`), and `signal-log.schema.json` one line of its day index `log/<type>/<yyyy-mm-dd>.jsonl`. `listener.schema.json` is a part, not a file: `naive-config.schema.json` holds `listeners` (each naming its consumer) and `listeners_off`, `frame.schema.json` holds `listens` (the frame is the consumer, and a frame's listener never projects), and `packages/naive/src/checks/check-data-model.mjs` checks a package manifest's `listeners`. A listener hears a type range, carries a criterion (a worst rating, producer prefixes and predicates whose operand is a literal, `{ "read": "<file>#<field>" }` or `{ "ids": "<collection>" }`) and then projects, proposes or revalidates; only edge listeners (propose, revalidate) may carry `max_age`. `knowledge-sources.schema.json` gives a source `carries`: records or signals. `competitor.schema.json` is a person's master record (`competitors/<id>.json`) and `competitor-signals.schema.json` what signals say about it (`competitors/<id>/signals.json`), which the data model marks `writer: projection`. The examples are in `examples/signals/`. The router enforces `writer: projection` (build item 4): only the signal projector writes such a record, and everyone else, a person included, is refused with the hint to emit a superseding signal (`writerRule` in `packages/naive/src/engine/gate.mjs`). The render and the pull are later build items, not built.
- `founder-idea.schema.json` is an idea a person owns. Its `relations[].relation` and `scope.via` take kebab-case names only (`builds-on`, `appends-to`, `derives-from`), from the relation table in [`packages/naive/src/terms/relations.ts`](../terms/relations.ts).
- `schemaFile` and `readSchema` take a name, `venture` or `venture.schema.json`, never a path.
- `recordPath` maps a stored repository path, as the data model and the package manifests name a schema (`packages/naive/src/records/venture.schema.json`), to the absolute file. A stored path under another folder, such as an app's `app/schemas/claim.schema.json`, resolves from the repository root. The prefixes it reads are listed in `PREFIXES`, so the move can accept `packages/naive/src/records/` and keep `schema/` for one release.
- `venturePaths(record)` gives a venture-level record type's paths relative to a venture folder. In `data-model.json` those paths carry the prefix `VENTURE_PREFIX` (`instance/**/`), the name the data model has always used for a workspace. It names no folder Naive reads, so code asks `venturePaths` instead of slicing the prefix.
- `pathKind(logicalPath, model)` says what kind of file sits at a logical path in a venture, so a host that commits a working copy knows what to do with it (hosted working copy design, section 2). A `record` is written whole through the store. A `log` is append-only, so a commit may only add lines at the end. A `derived` file is a cache Naive rebuilds, which a host may keep or drop. The kind comes from the matching record type's `kind` in `data-model.json` (default `record`), or from the data model's `files` entries, which name the venture files no record type covers: READMEs, briefs and charters in prose, and Naive's own files under `.naive/`. It returns null when nothing names the path, and throws when two matches disagree. A host passes the model it holds, and the patterns are compiled once per model. Today's logs are `provenance.jsonl`, `traces/<session>.jsonl`, `knowledge/freshness.jsonl`, `.naive/telemetry.jsonl`, `.naive/decision-index-history.jsonl`, `.naive/trigger-errors.jsonl`, `.naive/lint-findings.jsonl` and `.naive/events.jsonl`. The blob store `.naive/blobs/**` is a record kind: a blob never changes and an as-of read cannot rebuild it. The derived files are `.naive/decision-index.json` and everything under `.naive/cache/`, `.naive/types/`, `.naive/upgrade/` and `.naive/publish/`. `node packages/naive/src/checks/check-data-model.mjs` fails when a file in an example venture has no kind.
- `readDataModel` appends an app's own record types. An app that uses Naive, such as Mentura, keeps its record types out of Naive's data model and lists them in `naive.data-model.json` at the root of the repository being checked: `{ "records": [...], "ignore": [...], "files": [...] }`, each entry shaped as in `data-model.json`. Anything else in that file is refused. Every check that reads the data model then checks the app's records like Naive's. Naive itself has no such file.
- `schemaNameOf` turns a stored path into the name `node packages/naive/src/records/validate.mjs --schema` takes.
- `recordsIn(root)` gives the same functions for another copy of the repository, such as a test's temp copy (the `EE_ROOT` pattern of `packages/naive/src/checks/check-data-model.mjs`).

It is `.mjs`, like [`packages/naive/src/core`](../core/README.md), because most of its callers are `.mjs` and the published package runs on Node 20, which has no type stripping. Its test is TypeScript.

`node packages/naive/src/records/validate.mjs` validates records in JavaScript, with no Python and no dependency. It takes `--schema`, `--def` and `--file`. It is `.mjs` for the same reason as the resolver: the write path will import it, and an app runs it from `node_modules`, where Node does not strip types. It covers the JSON Schema 2020-12 keywords these schemas use and exits 2 on a keyword it does not know. Of the formats it checks only `date`, as Python's jsonschema does without optional packages. `node packages/naive/src/records/validate-test.ts` checks that it and jsonschema give the same verdict and the same failing paths on every record and on mutants of each; it runs where python3 with jsonschema is installed (CI has it) and says it skipped otherwise. Every runtime check calls it in process through `validateFile(schema, file)` or `validateValue(schema, value)`, which return what the command would (status 0 valid, 1 invalid with one `path: message` line each, 2 could not check), so the router, the engine, the CLI and the ontology gate run with no Python. `useValidator(v)` swaps in another `Validator`, for a host with schemas of its own or a test that needs a checker that cannot run.

## Run and test

- `node packages/naive/src/checks/check-record-paths.ts` fails when code outside this module builds a schema or data-model path from the folder name (`join(root, "schema", name)`, a path literal such as `"packages/naive/src/records/data-model.json"`, a concatenation, a stored path read by its prefix, or a Python `root / "schema"`). Its allowlist names each exception with a reason.
- `node packages/naive/src/checks/check-record-paths-test.ts` checks that every schema resolves by name and by stored path and that every schema the data model names exists, and breaks the check on copies.
- `node test.mjs` runs both.
