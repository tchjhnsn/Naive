# checks

Up: [src](../README.md)

## What this is

The checkers and lints. A checker reads a workspace, a venture or the repository, prints what holds and what does not, and exits 1 on a failure; it never edits a record. Lints answer through routes such as `money/lint` and `people/lint`. A symbolic check reaches the EE-095 term engine, `admit` or a Lean theorem (`packages/naive/src/terms/bypass-guard-test.ts`).

## Run and test

- `node packages/naive/src/checks/test.ts` breaks copies of the examples and the repository and checks each checker fails on them.
- `node test.mjs` runs each checker on the examples.

## How it connects

- Called by: `test.ts`, the router's check actions and CI.
- Calls: [`engine`](../engine/README.md), [`records`](../records/README.md), [`terms`](../terms/), [`core`](../core/README.md).

`check-config.ts` checks `naive.config.json` against its schema in process with `validateFile` from [`packages/naive/src/records/validate.ts`](../records/README.md), so no checker here needs Python. `premise-lint-test.ts` proves a failed proposal is reported by preloading a validator that cannot run (`useValidator`). It also holds `activity_proposals.rules` to the activity catalog (EE-170): each rule id is one of the catalog's proposal rules, and each line names a scale the catalog lists, inside its range. `check-activities.ts` reads a rule's lines with the same `lineProblems` from `packages/naive/src/engine/activity-proposals.ts`.
