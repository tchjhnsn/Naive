# recipes

Up: [engine](../README.md)

## What this is

The recipe sandbox, where a venture's recipes run, the eval sets and scoring that judge them, the starter recipe, and how the signal pull renders through recipes. A recipe is one pure TypeScript module per projected route pattern that makes the record at that pattern from the signals it hears and the facts it names, as of a time. It exports `hears` (the signal type ranges and named fact references it reads), `knobs` (a JSON object of numbers and short lists) and one synchronous default function `(input, knobs) => { record, receptions }`, with exactly one reception per heard signal. This folder is build plan item 4 of the autoresearch design (AUTORESEARCH_RECORDS_2026-11-06 in the design folder of the everything-ecosystem repository, "The recipe" and "The sandbox (Naive)"), an extension of the signal library design (SIGNAL_LIBRARY_2026-11-06 there). The nouns are proposed, not admitted.

Node's docs say `vm` is not a security boundary. This sandbox is layered defence, and no one layer is meant to hold alone:

1. Lint before a run: a size bound (64 KiB by default), types stripped with Node's `module.stripTypeScriptTypes`, no import of any kind (a type-only import is erased with the types), no name that starts with `__naive`, no backslash outside a literal, only the export forms `export const|let|var|function|class|async function`, `export default function`, `export default <expression>` and `export { a, b }`, and no string, template or regular expression literal that holds a subject id or signal address the caller passes. Comments and names are not literals. The lint does not see a literal built at run time (`"ac" + "me"`).
2. One child process per batch: `node --permission` with no file system, child process, worker or addon grant, fetch and WebSocket off, string code generation off, an environment of only `TZ=UTC`, a heap cap, a wall-time kill (SIGKILL) and an output cap. The child's code arrives with `-e`, so it needs no read grant, not even for itself. JSON crosses on stdin and stdout.
3. A fresh `vm` realm per call: an ordinary global object (`vm.constants.DONT_CONTEXTIFY`, so no host object sits behind the global), string and wasm code generation off, microtasks drained inside the call's timeout. A prelude, run as its own script so the recipe cannot shadow what it captured, makes `Date()`, `new Date()`, `Date.now()` and `Math.random()` throw and removes `Intl`, the locale methods, `WeakRef`, `FinalizationRegistry`, `SharedArrayBuffer`, `Atomics`, `WebAssembly`, `console` and `eval`. A date built from a given time still works. Values cross only as strings, and the realm hands back one string, so module state, globals and prototypes cannot carry from one call to the next.
4. The output check: JSON with exactly `record` (an object or null) and `receptions`, each reception an object with a string `signal` and a `kind` of `salient` or `noise`, one per signal in `input.signals` and none for a signal not heard. Schema validation of the record is the caller's job, through the `validateRecord` hook.

The hardening path is QuickJS compiled to wasm behind the same interface (not built).

### Eval sets and scoring (build plan item 5)

How a recipe is scored ("The metric", "The eval plan" and "Noise stored beside the record" in the design):

- **Settled record.** For a subject at as-of point t: the plain fold, as the signal types' own projections write it, of the settled claims with a valid time at or before t, known by t plus the horizon. Only people and producers settle a claim. A person's claim is a signal in the venture's local library (`raw/signals/`) whose provenance line names `agent.kind: "person"`, superseding signals included. A producer's claim is a signal in a library the venture reads (a filesystem source in `knowledge/sources.json` that carries signals), and it settles once a second producer reports the same claim (the same type, subject and the values its first append fold is unique by) or a person states it. A local signal an agent wrote, or one with no provenance line, settles nothing, so no agent can label its own work.
- **Losses.** Each field's loss is from the closed catalog in the record type's `settles`: `exact` (canonical JSON equal), `set-jaccard` (1 minus the Jaccard index of the two lists as sets; an entry's `signal` field is left out, so entries match by what they say) and `abs-scaled` (the difference over the scale, capped at 1). A forecast field is scored by Brier against whether a settled signal of its resolving types arrived within its window; a missing forecast counts as 0. A row's loss is the weighted mean of its fields; a null prediction of a settled record loses every field. A forecast resolved by a decision has outcome null and is left out (not built).
- **Rows and weights.** One row per subject and as-of point where the settled record or the plain fold is not null. `uniform` weighs each row 1. `cited` weighs a record 1 plus the number of provenance lines whose `derived_from` names its file and trace spans that mention it, by `read_cut`, at most 10.
- **Baseline.** The plain fold of every signal observed by t, whoever wrote it.
- **Dev verdict.** Paired rows only. The gain is the weighted mean of the tip's loss minus the candidate's, and the margin the larger of `min_gain` and twice the standard error of a block bootstrap (blocks of consecutive as-of points, the plan's `bootstrap` or 28 days and 1,000 resamples) drawn from a generator seeded by the plan's sha, so the same rows give the same verdict on every run. keep, better: the gain is above the margin. keep, smaller: the candidate has fewer tokens and the gain is at least 0. Otherwise discard. A recipe's first write is scored against the plain fold (`tip_score` null), and is never kept as smaller. fail: a lint failure, exports that fail `recipe.schema.json`, a throw, timeout or invalid output on training or dev, a record that fails its schema, a fact the plan did not freeze, or any noise disagreement.
- **Noise by ablation.** For every signal a recipe calls noise, the row is run again with that signal taken out of the index. A record that is not byte-identical is a disagreement.

`naive recipes plan <pattern> --by <person>` is a person's: it refuses with no `--by`, and when an agent is acting (`MENTURA_ACTOR` other than person, `MENTURA_MODEL`, or a `MENTURA_ACTOR_ID` other than `--by`). It draws as-of points on the record type's cadence from the first signal about the pattern's subjects to the time the plan is made less the horizon, about 60, 20 and 20 percent training, dev and holdout once two purges of more than the gap (the horizon unless `--gap`) are taken out, with `read_cut` the last training point plus the horizon. It refuses a gap shorter than the horizon, a forecast window longer than the horizon, a window with fewer rows than `min_counts`, a holdout that would reuse the previous plan's points, and a pattern without `[id]` (not built). It freezes `<venture>/_eval/<sha>/eval-set.json` (the points, every signal about the subjects observed by the time the plan is made with its library and who stands behind it, the signal types, each fact the current recipe names as `readAsOf` gave it at each point, and each row's settled record, plain fold, forecast outcomes and weight), then writes `<pattern>.plan.json` through the eval plan generator, and logs both in provenance as the person's. A library that backfills later cannot change a frozen set.

`naive recipes check <pattern>` runs the venture's recipe on the plan's training rows in the sandbox, with the inputs a render would give it at each point: every heard signal about the subject observed by t, in (time, id) order, withdrawn as known at t, and the frozen facts. It prints each row's loss and field losses, the settled loss beside the plain fold's, and every noise disagreement; `--json` adds the settled and predicted records. It exits 1 on a failure or a disagreement.

### Rendering through recipes (build plan item 9)

`naive recipes init <pattern> --by <person>` is a person's: it refuses when no person is named, an acting agent, a pattern that is not a projected record type with `[id]`, and a pattern that already has a recipe. It writes `<pattern>.recipe.ts` once and logs it in provenance as the person's, so its bytes are in the blob store. The starter is the plain fold, generated from the signal types the venture's libraries hold: data (the plain fold's listeners in order, the views of each signal type version a listener may hear, the signal itself or a composed part, and each view type's projection to the pattern) and a small fold over it, the signal library's reducers in (time, id) order. It renders exactly what the scorer's baseline renders. A signal of a type version it does not list is noise to it. A valid time reaches a recipe as milliseconds, so the starter writes a time at midnight UTC back as a date and any other as a UTC timestamp.

The signal pull ([`packages/naive/src/router/orchestration/signals.ts`](../../router/orchestration/signals.ts)) renders every pattern that has a live recipe through it, with what `render.ts` here decides:

- **Input.** Each touched subject as of the pull's `now`, the input `recipeInput` gives the scorer: every heard signal observed by then, in (time, id) order, withdrawn as known then, and the named facts read through the router as of now. All of a recipe's subjects run in one sandbox child, linted against the collection's ids and the signals given, and each record must pass its record type's schema. Any failure fails the pull before anything is written.
- **Records.** The listeners' render still runs whole, so proposals, marks and the ids other listeners read do not change; only the records at the recipe's pattern are the recipe's, each cited by the signals it called salient and the fact files it names. A null record writes nothing.
- **Receptions.** Beside each record it renders, `<record>.reception.json` through the reception generator: the record, the recipe's sha256, the render's as-of time, and per heard signal its kind, fields or reasons, valid and transaction times, `withdrawn_at` as known then, and the factors lag, age and the producer's confirmed and withdrawn shares (of the producer's signals observed before this one whose horizon passed by the render, the share a second producer or a person confirmed and the share retracted or superseded; null with none, or with no horizon). Uptake is null (not built). It is written with a new or changed record, and with an unchanged one only when what it says changed, so a pull after a pull writes nothing.
- **Hindsight.** Each pull, also one with nothing new, takes every receptions file of a live recipe's pattern whose as-of point plus the record type's horizon has passed and that has a reception with no label. The recipe that rendered it (the live one, or its source from the blob store) runs again at that point with every signal and once without each, and each record is scored against the settled record there (`settledRecord` and the forecast outcomes, only people and producers settling). Higher loss without the signal is helpful, lower is harmful, the same is inert, with both losses, the recipe's sha and the time. A label is never rewritten. The design says observed plus the horizon; the settled record at the render's point is final only at that point plus the horizon, so that is when every reception in the file is labelled.

### Knobs and probes (build plan item 10)

"With no model (graft: knob search)" and the optional probes in "Noise stored beside the record" in the design.

- **Knobs.** `knobs.ts` reads the `export const knobs = { ... }` literal from a recipe's source (types stripped first, so positions hold): each knob written as a literal number, quoted string, boolean or list of them, with the span of its value. A knob written any other way is skipped with why, and a spread, a computed name or a shorthand refuses the whole literal. `setKnob` replaces one value and leaves every other byte as it was; a number is written to six significant digits. `stepsOf(value, factor)` gives one step each way: a number is multiplied and divided by the factor (2 unless a search says otherwise), an integer stays an integer and moves by at least 1, 0 steps to 1 and -1, and a fraction strictly between 0 and 1 stays within 0 and 1; a boolean has one step, the other value; an Admiralty rating floor steps one grade looser and one stricter on both scales (B2 to C3 and A1). Any other string, and a list, has no step. `naive recipes search <pattern>` writes the steps through the router (`packages/naive/src/router/orchestration/recipe-search.ts`), because a step is an experiment write.
- **Probes.** `probes.ts` decides which noise a consumer surfaces anyway. `research.probe_rate` in `naive.config.json` (0 to 1, and 0 by default because probes cost attention) is the share; a signal is probed when the first 52 bits of sha256 of the record's path and the signal's id, as a share, fall below it, so the probed share does not move when the recipe changes, a higher rate probes every signal a lower one did, and two records that hear one signal draw apart. `markProbes` adds `probe: { rate }` to each probed noise reception, which `reception.schema.json` allows on noise only. A reception's propensity is 1 when salient, the rate when probed noise, and 0 otherwise. `ipwEstimate(logged, surfaces)` estimates a candidate recipe's mean outcome from what a current one logged: each surfaced signal with an outcome that the candidate also surfaces counts with weight one over its propensity (Horvitz and Thompson), beside the self-normalized mean and Kish's effective sample size, so a recipe that would surface what the current one calls noise is scored on the probes. The signal pull writes reception files (build plan item 9) but does not mark probes in them yet, and the outcomes of probed signals (what a person made of each) are not built.

## Where things are

| [`sandbox.ts`](./sandbox.ts) | The host. `runRecipe(source, input, knobs, opts)` runs one call (`knobs` null runs the recipe's own), `runRecipes(source, calls, opts)` runs a batch in one child, `recipeExports(source, opts)` reads `hears` and `knobs`, `lintRecipe(source, opts)` lists every lint problem, `checkReceptions(input, receptions)` checks coverage. Each answers `{ ok: true, output }` or `{ ok: false, reason }`. | [`sandbox-child.ts`](./sandbox-child.ts) | The child: reads one job, compiles the prelude and the recipe once, runs each call in a fresh realm, writes one reply. The host strips its types and starts it with `-e`; nothing imports it. |

| [`knobs.ts`](./knobs.ts) | Pure. `knobsIn(source)`, `setKnob(source, name, value)`, `formatKnob` and `stepsOf(value, factor)`. |

## Run and test

- `node packages/naive/src/engine/recipes/scoring-test.ts` tests the losses, Brier, the seeded bootstrap and the verdict, and that only people and producers settle a claim. `node packages/naive/src/engine/recipes/eval-set-test.ts` plans on temporary ventures with two signal libraries and proves the item's verifier: the windows are purged (each training row settles from the signals observed by `read_cut` alone, and a short gap is refused), an agent's local signal changes no settled record or outcome while a person's does, and the dev verdict is identical over two runs and when the set is read again; it also shows a keep as better, a keep as smaller, a discard, a throw and a noise disagreement failing, and `naive recipes plan` refusing an agent. `node test.mjs` runs both.
- `node packages/naive/src/interfaces/tests/recipe-render-test.ts` tests init and rendering through recipes end to end over two ventures (the starter equals the plain fold, one signal is salient at one venture and noise at the other, hindsight is written past the horizon and only once, and a second pull writes nothing). `node test.mjs` runs it.
- `node packages/naive/src/engine/recipes/sandbox-test.ts` renders the example recipe; shows the clock, randomness, `new Function` and `eval`, static and dynamic imports, an endless loop (killed at the wall time, and by the per-call limit, also in a microtask), state between calls, the heap cap, the file system (`require`, `process`) and the environment (`process.env`, `Intl`) each fail closed; checks the lint and the reception coverage; and times 1,000 calls with 40 signals each in one child (about 1.5 to 3 seconds on Node 22.23). `node test.mjs` runs it.
- `node packages/naive/src/engine/recipes/knobs-test.ts` and `node packages/naive/src/engine/recipes/probes-test.ts` test knobs and probes. The search is tested end to end by `node packages/naive/src/interfaces/tests/recipe-search-test.ts`. `node test.mjs` runs all three.

## How it connects

- The sandbox is called by `eval-set.ts`, `starter.ts` and `render.ts`, and by `packages/naive/src/checks/check-recipes.ts` (build plan item 11), which lints each recipe, reads its exports and renders each record that has a reception file again, with and without each noise signal, with the same input builder (`recipeInput` in `outcomes.ts`). The signal pull calls `render.ts` and `loadSignals` in `eval-set.ts`. `scoreExperiment` is called by the router's recipe route ([`router/recipes.ts`](../../router/recipes.ts), build plan item 6), which scores every write to `recipes/<pattern>` inside the write.
- The sandbox calls Node's `node:child_process`, `node:vm` and `node:module` only. It imports nothing in the repository and spawns only `process.execPath`, never a command an environment variable names.
- `outcomes.ts` reaches the signal render through its front door, `engine/signals.ts`. `eval-set.ts` reads provenance and traces (`core/`), the data model and schemas (`records/`), facts as of a point (`store/as-of.mjs`) and the eval plan generator.
- Records: `naive recipes plan` reads the venture's signal libraries, `provenance.jsonl`, `traces/` and the recipe, and writes `<pattern>.plan.json` and `_eval/<sha>/eval-set.json`. `naive recipes init` reads the libraries' signal types and writes `<pattern>.recipe.ts`. The signal pull reads recipes and writes receptions as the projector. No agent reads `_eval/` through the router.

## Not built

- Holdout checks are not built: autoresearch build plan item 8. Marking probes in the reception files the pull writes, rendering a pattern without `[id]` through a recipe, uptake, and `explain` showing a recipe's receptions are not built.
- The cross-file check of what exists, `packages/naive/src/checks/check-recipes.ts`, is built (item 11).
- Forecasts resolved by a person's decision have outcome null, a plan for a pattern without `[id]`, and libraries in connectors other than filesystem are not built. Their schemas exist (item 3, `packages/naive/src/records/recipe.schema.json`, `eval-plan.schema.json`, `experiment.schema.json` and `reception.schema.json`), and the data model's recipe record type covers this folder's fixture.
- Record and reception types generated from JSON Schema through `naive typegen`; the fixture and the example recipe in `packages/naive/src/records/examples/signals/` declare their own types.
- Type stripping needs Node 22.13 or later. On an older Node every recipe fails closed with that reason.
- QuickJS compiled to wasm as a second realm behind the same interface.
