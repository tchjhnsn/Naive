# packages/naive/lean/

Proofs that settle Naive's definitions. When a term is contested (is this person a founder? is every co-founder a founder?), the answer comes from running a check or a proof, not from asking someone how it was defined.

- `Naive/Concept.lean`: the engine. A concept is a list of named, decidable properties; `passes`, `failed` (why not), `IsA`, `Disjoint`, and `refine_isA` (adding properties narrows a concept).
- `Naive/Terms.lean`: the relation is total (R3); every phase gate is a threshold guardian; admitting a term keeps term ids unique, and by induction any sequence of admissions does (§23); the idea relations of the term typed-link pair their inverses, and a relation and its inverse share one order, so reading narrower backwards keeps the cycle check sound (S2-PR9).
- `Naive/Founder.lean`: founder (P7, F1 to F5) and co-founder. Proves every co-founder is a founder, unconfirmed facts never make a founder, and an unevidenced contribution never counts. `decide` settles single cases.
- `Naive/Layer.lean`: layer in the technical sense. An order that every dependency points down rules out a cycle (`downward_order_no_cycle`), so a cycle rules out every such order (`cycle_no_downward_order`), and EE-001's five looping groupings have none (`ee001_loop_no_downward_order`). A witness shows the ontology's three have one.
- `Naive/Upper.lean`: the upper ontology (N-049). For every hierarchy joined by broader links: a rank that each link lowers rules out a cycle (`upper_no_cycle`); a top category with nothing broader reaches only itself (`upper_top_only_itself`); a rank that each link lowers and no orphan give every category a top category (`upper_reaches_top`), and on a finite hierarchy no cycle gives such a rank (`upper_rank_of_no_cycle`); a category that each top category keeps and each link preserves makes it unique (`upper_top_unique`, `upper_one_top`); a rank that each link lowers, no orphan and no category reaching two top categories give such a category (`upper_cat_of_u4`, `upper_one_top_of_u4`); a finite hierarchy with no cycle has a rank that each link lowers (`upper_rank_of_no_cycle`), so on a finite hierarchy the three checks the code runs give every category exactly one top category (`upper_one_top_of_checks`); and links that are is_a make a noun is_a its top category (`upper_isA_top`). The term `top-category` in `packages/naive/src/terms/terms.ts` cites these theorems, and `node packages/naive/src/terms/upper-test.ts` runs it on `packages/naive/src/terms/ontology.json`. What is proved is that the hypotheses give exactly one top category; that the code's checks state those hypotheses is read off the code, not proved. Core Lean, no `Concept` definition, so it needs no admitted term of its own.
- [`Naive/Detection.lean`](./Naive/Detection.lean): signal detection ([`SIGNAL_DETECTION_2026-11-07.md`](../../../docs/design/SIGNAL_DETECTION_2026-11-07.md)). The call is yes when the score is at or above the criterion. For every ledger: the optimal criterion rises with the noise base rate and the false alarm cost and falls with the miss cost, stated on the expected value rule (`criterion_monotone`); moving the criterion up never raises the hit count or the false alarm count (`roc_monotone`); at every criterion the signal trials split into hits and misses and the noise trials into false alarms and correct rejections (`outcomes_partition_signal`, `outcomes_partition_noise`); the trapezoid area under the empirical ROC curve equals the two-alternative proportion correct on the same scores, ties counting half, when the criteria descend through every observed score (`auc_eq_2afc`); and for every criterion either an observed score has the same empirical cost or every call is no (`best_criterion_observed`). Scores are integers and likelihoods and costs natural numbers, so a rational one is scaled by a common denominator first. The terms `detector`, `trial`, `hit`, `miss`, `false-alarm` and `correct-rejection` in `packages/naive/src/terms/terms.ts` cite these theorems. Core Lean, no `Concept` definition, so it needs no admitted term of its own.
- [`Naive/Recipes.lean`](./Naive/Recipes.lean): autoresearch over venture records (AUTORESEARCH_RECORDS_2026-11-06.md in the everything-ecosystem repository). A recipe makes every record at one route pattern from what is known as of a time; an experiment is one write of it, scored inside the router against a frozen eval plan. For every log, plan and recipe: nothing written or observed after `t` changes a record read as of `t` or the signals heard by `t`, so a pure recipe run as of `t` renders the same record (`as_of_no_lookahead`); every training outcome settles before the first dev point, every dev outcome before the first holdout point, and every holdout outcome by the time the plan was made (`windows_purged`); the researcher reads nothing in the eval set and nothing written at or after a holdout point changes what it reads (`holdout_unread`); with no disagreement from the check, a signal called noise leaves the record byte-identical when removed, so its hindsight label is inert (`noise_inert`); the verdict ignores the score the writer claims, who wrote and the clock (`verdict_deterministic`), a retried write returns the logged line and spends nothing (`retry_spends_nothing`), and a failed row discards (`failed_row_discards`); and a claim is settled only by a person or two distinct producers, so agent statements never change it (`agent_never_resolves`, `agent_alone_settles_nothing`). The terms `experiment`, `kept-experiment`, `discarded-experiment`, `eval-plan` and `settled-record` in `packages/naive/src/terms/terms.ts` cite these theorems. Core Lean, no `Concept` definition, so it needs no admitted term of its own.
- [`Naive/Signals.lean`](./Naive/Signals.lean): the signal library (SIGNAL_LIBRARY_2026-11-06.md in the everything-ecosystem repository). A listener hears a signal when it names the signal's type or a part's type, and the reception is salient when the listener's criterion (rating bounds and predicates over the venture's facts) holds and noise when it fails. For every signal and listener: every signal is salient at one listener and noise at another under the same facts (`noise_relative`), so no property of the signal alone defines noise (`noise_undefinable`), and one fact changing can turn the same reception from salient to noise (`noise_relative_facts`); a heard signal is salient or noise and never both, an unheard one neither (`noise_salient_partition`), and the heard signals of a list split into the two (`noise_salient_count`); a signal withdrawn by a log stays withdrawn as the log grows (`withdraw_monotone`, `live_shrinks`), counting a retraction only from the signal's producer or a person in the local library; after a commit the diff is empty (`reconcile_idempotent`), committing twice is committing once (`commit_idempotent`) and an empty diff changes no record (`unchanged_not_rewritten`); and a listener for a part's type hears every composite with that part (`part_heard`, `heard_iff`). The terms `signal`, `listener`, `reception`, `salient-reception` and `noise` in `packages/naive/src/terms/terms.ts` cite these theorems. Core Lean, no `Concept` definition, so it needs no admitted term of its own.
- [`Naive/Generated/Ontology.lean`](./Naive/Generated/Ontology.lean): generated, never edited by hand. `node packages/naive/src/terms/gen-concepts.ts` writes one concept per noun in [`packages/naive/src/terms/ontology.json`](../src/terms/ontology.json) (EE-014), inside `namespace Ontology`. The ontology records a noun's meaning as prose and its placement as data, so each concept's properties check placement only: `level <level>` always, and `function <id>` when the noun names a function. The facts are `Placement` (a level and an optional function), with no label field. Two nouns with the same placement pass the same facts, so these concepts can prove two nouns apart only by placement (the two senses of customer, `customer_finance` and `customer_marketingAndSales`, are disjoint); telling nouns apart by meaning takes an admitted term. The file's header states that limit. The noun, meaning, standard and status sit in each docstring, followed by every other field the noun carries (`handoff_type`, `references`, `replaced_by` and the rest, sorted by key), so editing any field of a noun changes the file. Names: lower camel case of the noun's ASCII letter and digit runs, with a scope after `@` joined with `_` (`customer@finance` is `customer_finance`); two nouns with one name stop the generator. Every name, the `Level` and `Department` constructors included, is written in Lean's `«»` quotes (`«customer_finance»`), so a noun that is a Lean keyword (`sorry`, `syntax`) or starts with a digit still parses, with no keyword list. The quotes are not part of the name, so other files write `customer_finance`. The checks call `Decidable.decide` and `Option.some` by their full names, so a noun named `decide` or `some` cannot shadow them. An ontology with no nouns stops the generator with exit 2. `node packages/naive/src/terms/gen-concepts.ts --check`, which `test.mjs` runs, fails when the file differs from a fresh run. It is regenerated whenever a noun is proposed, most recently `handoff claim` (lead agents, build plan item 5).
  The nouns the lead agents design proposes reach this file the same way: `spend register` (function finance) and `access matrix` (lead agents build item 2) are concepts with placement checks only.
- [`Naive/StandingRules.lean`](./Naive/StandingRules.lean): Wilson lower bound for earning a standing rule, and the floored Wald SPRT for losing one. Each theorem is stated in plain language in [`STANDING_RULE_LEARNING_2026-11-02.md`](../../../docs/design/STANDING_RULE_LEARNING_2026-11-02.md).

Build: `cd packages/naive/lean && lake exe cache get && lake build` (toolchain pinned in `lean-toolchain`; install with elan). [`Naive/StandingRules.lean`](./Naive/StandingRules.lean) uses Mathlib for real square roots and logarithms, and `lakefile.toml` builds it as its own root (`Naive.StandingRules`) so Mathlib is not imported beside `Naive.Concept`. The other files stay in core Lean. `lake exe cache get` downloads Mathlib's build cache. CI does that and then `lake build`. The cache lives under `.lake/` in this folder, which `eslint.config.mjs` ignores.

The names here and the term engine are tied together by `node packages/naive/src/terms/lean-agreement-test.ts`, which `test.mjs` runs. It fails, naming the theorem, when a term in `packages/naive/src/terms/admitted.json` cites a theorem that no `.lean` file in `Naive/` declares. Declared means a line that starts with `theorem <name>` once Lean comments are removed. It also fails when a Lean concept has no admitted term. It reads every `.lean` file under `Naive/`, subfolders included. A Lean concept is a top-level `def` or `abbrev` whose declared type is `Concept <facts>`, named plainly or in `«»` quotes (the quotes are dropped from the name), so `founder`, `coFounder`, `thresholdGuardian` and `phaseGate` are concepts, and their admitted ids are their names in kebab case (`co-founder`). Helpers are told apart by type: fact structures, witnesses such as `jobs`, property pairs and functions are not of type `Concept`. A new concept therefore needs an admitted term in the same change. One file is exempt: `Naive/Generated/Ontology.lean`, because its concepts are ontology nouns, not glossary terms (EE-095), and `gen-concepts.ts --check` pins it to `packages/naive/src/terms/ontology.json`. Any other file, in `Generated/` or elsewhere, is held to the rule. `--root <dir>` checks one tree only. The test ties names, not meanings: the `lean` workflow builds the proofs, and it now runs when `packages/naive/src/terms/` or `packages/naive/src/terms/ontology.json` changes as well as `packages/naive/lean/`.

Conventions follow spct-lean: every property is a check that can fail; the facts carry no label field, so no check can read one.
