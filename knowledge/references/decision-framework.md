# Decision Framework

This framework guides strategic decisions about what to build, when to build it, and how it fits into the
ecosystem. Use this when the user faces a specific decision — not when they're creating or analyzing an entity
profile (use Discovery or Analysis mode for those).

---

## Decision Type 1: Does This Idea Belong in the Ecosystem?

When the user has a new idea and needs to determine whether it serves the ecosystem's mission.

**Walk through these questions in order:**

1. **What is the ecosystem's mission?** (If not clearly stated, help the user articulate it first.)
2. **Does this idea serve the mission?** Be honest. Not everything that's interesting or profitable serves
   the mission. If it doesn't serve the mission, it may be an excellent idea that belongs somewhere else —
   or it may be a distraction.
3. **If yes — what role would it play?** Would it fill a gap in the ecosystem? Would it reduce a dependency?
   Would it strengthen an existing entity? Would it open a new market aligned with the mission?
4. **If no — is the mission wrong, or is the idea wrong?** Sometimes a compelling idea reveals that the
   mission needs to be expanded. Sometimes it reveals that the idea, however good, is simply not aligned.
   Help the user distinguish between the two.
5. **If the idea belongs — what is it?** Run Discovery Mode to classify it.

---

## Decision Type 2: What Should We Build Next?

When the user has multiple possible next steps and needs to determine sequencing.

**Walk through these questions:**

1. **What exists right now?** Review existing entity profiles. What's in production? What's in progress?
   What's conceptual?
2. **What does the mission demand next?** Not what's most exciting, not what's easiest — what does the
   mission actually require as the next step?
3. **What are the prerequisites?** For each candidate, what must already exist before it can succeed?
   Does the ecosystem have those prerequisites?
4. **What creates the most compounding value?** Some entities, once built, unlock the ability to build
   many other things. These high-leverage entities should generally come first.
5. **What are the dependencies and risks?** Is the ecosystem currently dependent on an external entity
   for something critical? If so, building sovereignty over that dependency may be more urgent than
   building something new.
6. **Which pillar should we start with for this entity?** There's no universal order. For some entities,
   product comes first. For others, brand comes first (like Cluely). For others, the business model should
   be validated before anything else is built. Help the user determine the right starting pillar for this
   specific entity at this specific moment.

**Present your recommendation with reasoning.** "Based on what exists, the mission, and the prerequisites,
I recommend [X] as the next build because [reasoning]. The alternative was [Y], but [why X is better timing]."

---

## Decision Type 3: Horizontal, Vertical, or Diagonal?

When the user is considering an expansion and needs to determine the type of move.

**Walk through these questions:**

1. **What is the proposed expansion?** Describe it clearly.
2. **Is it at the same level of the value chain as existing entities?** If yes → likely horizontal.
3. **Is it at a different level of the value chain — upstream or downstream?** If yes → likely vertical.
4. **Does a horizontal move create a vertical integration opportunity with another entity?** If yes →
   diagonal movement. This is especially valuable and worth noting explicitly.
5. **Can the existing entities succeed without this expansion?** If yes, the expansion adds value but
   isn't critical. If no, the expansion addresses a dependency — which increases its urgency.
6. **Will this expansion be independently viable?** Horizontal adjacencies must be able to succeed on
   their own. If the expansion would need to be permanently subsidized by existing entities, flag this
   as a structural risk.

---

## Decision Type 4: Should This Be a Subsidiary or a Product Within the Company?

When the user has an entity that could go either way.

**The key distinction is separation of operations and identity:**

- **Subsidiary indicators:** It has or will have its own brand that users identify with independently.
  Its operations are or will be distinct from the parent's core operations. It could exist as its own
  company if separated. It serves a different market or audience than the parent's core products.
  Examples: Waymo (Alphabet), WhatsApp (Meta).

- **Product-within-company indicators:** It ships under the parent's brand. Its operations are integrated
  with the parent's operations. It serves the same or adjacent audience as other products. Separating it
  would feel like removing a feature rather than spinning out a company. Examples: Tesla Optimus, Apple AirPods.

**If it's genuinely ambiguous**, it may be an entity that's currently a product but is growing toward
subsidiary status. Note this trajectory in the entity profile. Some entities start as products and
evolve into subsidiaries over time (YouTube started as an acquisition and became a distinct brand
within Alphabet).

---

## Decision Type 5: Archive or Continue?

When the user is considering discontinuing an entity.

**Walk through these questions:**

1. **Why is discontinuation being considered?** (Market failure, strategic pivot, resource constraints,
   mission misalignment, something else?)
2. **Does this entity serve the mission?** If not, discontinuation may be correct regardless of other factors.
3. **Is the problem with the entity itself, or with its current execution?** Sometimes the right answer
   is not to discontinue but to pivot — same mission alignment, different approach.
4. **What would be lost?** Users, brand equity, strategic position, institutional knowledge?
5. **What would be gained?** Resources freed up, focus restored, strategic clarity?
6. **If discontinued, what happens to its dependencies?** Do other entities depend on this one?
   Will discontinuation create a gap that needs to be filled?

**If the decision is to discontinue:**
- Archive the entity profile — do not delete it
- Record the date, reason, and what (if anything) replaces it
- Record lessons learned
- Update relationship maps for affected entities

## General Decision Principles

These apply across all decision types:

- **The mission is the filter.** When in doubt, return to the mission. Does this serve it?
- **Independence is strength.** Entities that can succeed independently make the ecosystem resilient.
  Entities that need to be subsidized are structural risks unless the subsidy is time-bound and intentional.
- **Sequencing matters more than speed.** Building the right thing at the right time beats building
  the right thing at the wrong time.
- **Name the ambiguity.** If a decision is genuinely unclear, say so. Present the options, the tradeoffs,
  and let the user decide with full information.
- **Preserve the thinking.** Whatever decision is made, the reasoning should be documented in the entity
  profile changelog or the idea dump. Decisions that are well-documented can be revisited; decisions that
  are undocumented are lost.
