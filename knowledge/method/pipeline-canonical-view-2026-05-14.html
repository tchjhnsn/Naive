SAD v3.3+ — Canonical Pipeline View

Project-agnostic reference. Captured 2026-05-14. Last-reviewed 2026-05-14 (revised same day through §27–§39 refinements).
Authored as Step 1a of the V1-next triage exercise — separate the methodology from any one project so we can map projects onto it. Revised across several iterations: enumeration is a mode of 0A (not a sub-phase); triage is the 0A→0B bridge; project ambition is declared before research; research is per-pillar, multi-mode, and runs in two passes; AI thought-partnership has two declared modes (friend / office hours); pillars are recursive; templates are explicit-on-what-to-consider but implicit-on-how-to-document; methodology produces role-filling artifacts when teams form; orchestration trajectory is HTML now and software later.

What this is. A single-page view of the methodology as it stands today — Articulate → Build → Ship → Operate, the three pillars that flow through every lane, the sprint anatomy that bounds every unit of work, the rituals that prevent silent drift, and the ratified-vs-proposed status of each amendment.

What this is not. A re-derivation of SAD from first principles, or a per-project application. The canonical document is knowledge/method/SAD_SKILL_v3.md. This is its operational sketch — the shape you'd want in front of you at the start of any sprint.

Two foundational principles to keep in mind (per §36–§37). (1) The three-pillar structure is recursive — pillar products are themselves companies-in-miniature with their own three pillars. (2) Templates are explicit about what to consider, implicit about how to document — they encode principles, recommendations, and examples; the actual deliverable shape is per project, per AI conversation, per context.

1. The four lanes

Every entity that gets shipped passes through the same four lanes in the same order. Lanes are recursive — a single version, a single surface, or a whole ecosystem all flow through them. Within a lane, phases are sequential; across lanes, work can run in parallel (e.g., V[N+1] Articulate often runs while V[N] is still in Operate).

Articulate
Turn an idea into a spec stack + design substrate that an implementer can build from without inferring intent
0A Mind Dump + Thought Partnership. → IDEA_MAP.md + (optionally) an enumeration artifact. Runs in two modes: free-form (loose, exploratory) and enumeration (systematic, breadth-first). Enumeration is a mode, not a sub-phase. AI posture: friend mode. v3.3+ §27
0A→0B bridge Triage. → Organize ideas (idea-dumps + enumeration artifact) into per-pillar categorization + prioritization + research-driving questions + row-level status (OPEN/TRIAGED/DEFERRED/etc.). Gate: research can proceed from triage outputs. v3.3+ §28
0Δ Project Ambition Gate. → Declare ambition tier: hobby / side-project / open-source-tool / venture / enterprise. Tier determines depth + breadth of research that follows. Stored in entity profile frontmatter. v3.3+ §29
0B Research (per-pillar, first pass). → Per-pillar RESEARCH_SYNTHESIS (product / brand / business). Web search + vault context, ambition-tier-calibrated depth. AI posture: friend mode — expand what's possible, broaden aperture. Output feeds 0C vision. v3.3+ §30
0C Unconstrained Vision. → VISION_SPEC.md (permanent; never scoped down). Arrived at via friend-mode research; captures what's possible across the full aspiration.
1A Version Scoping (office-hours mode). → VERSION_SPEC_v[N].md (subtractive cut of vision for this version). AI posture: office hours mode — sharp critique, demand evidence, kill weak claims. v3.3+ §31
0B′ Research (validate pass, post-1A). → Office-hours mode research that asks: are the versions tangible? Is the idea actually needed? May trigger regression to 1A or 0C. Output gates entry to 1B. v3.3+ §30
1B Spec Stack. → PRODUCT_SPEC, DATA_MODEL_SPEC, IMPL_SPEC, BEHAVIORAL_SPEC, VERIFICATION_SPEC. Spec Convergence loop runs to threshold.
1B.Final Cross-Spec Final Review. → PHASE_1B_FINAL_REVIEW.md. Consistency across all six specs at thresholds.
1C Articulation Closure amendment → UX/UI deliverables inventory + cross-spec gap audit + Ralph Wiggum test. Gate before Build can start. See §17 in build-roadmap idea-dump.
Build
Implement the spec stack against the verification gate — autonomously or with checkpoints
2.1 Bootstrap. → Repo init, framework + runtime parity (local preview = production runtime), CI scaffold, env wiring. v3.0.1 amendment — local-dev-parity-by-bootstrap
2.2 Schema. → Data model → migrations → seed contract. Type-check clean before next phase.
2.3 Platform. → Hosting target, database connection, runtime bindings, observability scaffold.
2.4 F-flow Vertical Slice. → One end-to-end user path implemented all the way through. Real-Run Smoke gate. v3.0.1 amendment — phase-closure-protocol
2.5 Editorial / Content Seed. → Real content lands; not stub. Vintage stamps on every record per spec.
2.x F-flow Expansion + Surface Buildout. → Remaining F-flows; remaining wiki surfaces; component library applied; design tokens consumed everywhere.
2.Final Verification Gate. → VERIFICATION_SPEC §9 test plan executes; PASS / FAIL on every row; failing-must-be-zero condition. Functional, not structural. amendment §12 — functional completion conditions
Ship
Move the verified build to production and confirm the user-facing surface is intact
3.1 Preflight. → Deploy checklist; lockfile + package.json paired; brand-load-bearing files surfaced; commit hygiene. amendments §13–§16
3.2 Deploy. → Production deploy executed; deploy logs reviewed; rollback path documented.
3.3 Post-Ship Verification. → Sitemap crawl; visual sweep; production §9 + advisory tests. Surface drift relative to spec.
3.4 Ship Handoff Doc. → What shipped, what's known-broken, what's next, what's in V[N].x patch queue.
Operate
Maintain the shipped surface, capture lessons, prepare the next articulation
4.1 V[N].x Patch Queue. → Bug fixes, data corrections, micro-polish. Doesn't expand scope; doesn't move the next-version line.
4.2 Monitor + Triage. → Observability reviews; incident response; runbook execution.
4.3 V[N+1] Articulate (parallel). → Next-version Articulate lane runs concurrently with V[N] Operate. Sprint type determines which lane the current session belongs to.
4.4 Methodology Amendments. → Lessons from Sprint N encoded as SAD v3.x+ amendment proposals. Captured in build-roadmap idea-dump, formalized in methodology repo.

2. The three pillars

Every entity has at most three pillars (per the vault constitution): Product (what the entity does), Brand (identity / voice / source-of-truth-for-look-and-feel), Business (commercial surface). Each pillar contributes its own deliverables at each lane.

Each pillar can have products. Product pillar holds canonical company products (required); Brand and Business may have products as optional extensions (podcasts, brand campaigns, partnership programs, training certifications, etc.). The product-type taxonomy (software / content / service / hardware / hybrid / partnership / program) is orthogonal to which pillar holds the product. §35

The pillars are recursive. Pillar products are themselves companies-in-miniature with their own three-pillar structure. A Brand-pillar podcast has its own Product (the show), its own Brand (the show's identity), and its own Business (operations, overhead, revenue). The methodology applies fractally — articulation closure, version-identity, deliverable templates work the same way at every recursion level. This is how companies organically birth other companies. §36

Product pillar

The spec stack + design substrate + code. SAD v3 was originally written here.

  • IDEA_MAP, RESEARCH_SYNTHESIS
  • VISION, VERSION, PRODUCT, DATA_MODEL, IMPL, BEHAVIORAL, VERIFICATION specs
  • Sitemap, IA, audience, UX flows, microcopy, content models
  • Wireframes, component library, responsive breakpoints, a11y checklist
  • Repo code, migrations, tests, deploy workflow
  • SESSION_LOG (institutional memory)

Brand pillar

Source of truth for identity. Imported by Product.design and Business — never copied.

  • Brand identity (colors, typography, logo, imagery style)
  • Brand voice + tone + narrative + microcopy register
  • Wordmark, mark, favicon, OG image, asset library
  • Foreshadowing discipline + invariants (e.g., I1–I9 for the reference project)
  • Version-identities + persona-evolution (for products with persona discipline)

Business pillar

Commercial / operational surface. Applies brand to commercial artifacts; never redefines brand.

  • Marketing site copy (landing, about, privacy, terms)
  • App store listing, preview briefs, social copy
  • Pricing, partnership memos, anti-scraping / ToS clauses
  • Metrics framework, operational runbooks, incident response procedures
  • Pitch decks, investor materials, contracts

4. Sprint anatomy

A sprint is a bounded work unit within a phase or sub-phase that produces a defined deliverable and closes against a gate. The sprint-declaration ritual at session start makes scope deterministic. See build-roadmap idea-dump §23.

FieldValues / Examples
Type articulation · build · ship · operate · methodology
Idea-state blank · articulated · built · shipped · re-articulating (§22)
Goal The deliverable. Named, bounded, attributable to a spec or amendment
Gate Functional, not structural. "User can do X" beats "Y route renders." (§12)
Dependencies Predecessor sprints whose gates must close before this one starts
Pillars touched Product / Brand / Business — one, two, or all three
AI posture Friend (sympathetic expansion) · Office hours (sharp critique). Declared per sprint. (§31)
Relations Sequential · parallel (within lane) · recursive (nested sub-sprints) · cross-cutting (methodology sprint between any two)

AI thought-partnership modes §31

The AI thought-partner operates in two modes. The mode is declared at sprint start as part of the sprint declaration ritual. Wrong-mode runs are themselves a methodology failure mode.

ModePostureDominant in
Friend mode Sympathetic expansion. "Yes, and." Help the operator broaden, see possibilities, articulate aspirations. Push back lightly when warranted but lean toward expansion over constraint. 0A (mind dump), 0B-initial (vision-expanding research), 0C (unconstrained vision), methodology brainstorming, any phase where the operator is exploring rather than converging.
Office hours mode Sharp critique (Gary Tan's Office Hours format as canonical reference). Press hard, demand evidence, identify weakest claim first, run steel-mans, surface the inconvenient question. Push operator to defend the strongest version of their thinking. 1A (version scoping), 0B′-validate (testing version tangibility / need), 1B spec convergence reviews, phase closure reviews, any phase where weak claims need to die before they ship.

5. Substrates

Skill layer vs. Wiki layer (SAD v3 PART 0)

SAD is both a Skill (capabilities the AI invokes — procedures, phase gates, session protocol, rituals) and a Wiki (knowledge the AI reads — spec artifacts, entity profiles, idea-dumps, methodology corpus). v2 over-developed Skill; v3 treats them as co-equal.

Raw vs. Compiled (SAD v3 PART 2)

Raw is immutable (only added; never edited). Compiled is re-buildable from raw. Five timestamp fields detect staleness: created, ingested, updated, last-compiled, last-reviewed. A compiled artifact whose upstream raw is newer than its last-compiled is stale.

Canonical-doc discipline §26 (proposed)

Every concern has exactly one canonical document. The canonical doc declares itself canonical in a top-of-document banner. Related documents cross-reference the canonical doc and declare their relationship (derives-from, elaborates-on, supersedes). Canonicalization is itself a methodology sprint output.

Idea archive §25 (proposed)

Every project at every level carries an idea-archive document. Archived rows record original framing, when tried, what happened, when/why rolled back, future notes. The Meta-rollback pattern — track your decisions about decisions.

6. The rituals

Session-start ritual at session start
  1. Step 0 — Declare scope level. Global / Project / Local. If Project, name the entity.
  2. Invoke time-awareness skill — record session-start-time (UTC ISO-8601).
  3. Invoke session-capture skill — capture predecessor session tail to _sessions/raw/.
  4. Read context: vault CLAUDE.md (or repo CLAUDE.md for code work), most-recent SESSION_LOG entry, entity profile + relevant specs.
  5. Declare sprint type + idea-state + goal + gate + dependencies. v3.3+
  6. Check unresolved staleness markers.
Session-end ritual at session close
  1. Invoke time-awareness — record session-end-time.
  2. Invoke session-capture — write the session's raw _sessions/raw/<date>-<slug>.md.
  3. Append compiled entry to _sessions/SESSION_LOG.md.
  4. Graduate any session-proposals that were executed; spawn new ones for follow-on work.
  5. Update status columns on enumeration / backlog rows touched this sprint. §24
Convergence loop at every ★ checkpoint

Spec Convergence (Phase 1B): < 10% ambiguity on critical specs, < 20% on others. Implementation Convergence (Phase 3): ≥ 95% compliance. Passing convergence produces handoff readiness — the artifact is intelligible to someone not in the room.

Cross-spec gap audit at Articulation Closure (1C)

Three-direction audit: forward (entities → UX), behavior (states → UX), flow (PRODUCT_SPEC F-flows → UX flows). Until clean (no red entries), Phase 2 does not begin.

Real-Run Smoke at Phase 2.x closure

Before declaring any Phase 2.x complete with external integrations, run the slice end-to-end against real services in a local preview environment. Surface surprises before they surface in production. v3.0.1 amendment.

Pre-commit ritual before every git commit
  1. Run git diff --stat HEAD; surface every file with its session-of-origin.
  2. Brand- and scope-load-bearing files: explicit "yes, ship this" confirmation.
  3. If package.json is staged, lockfile must also be staged. (§16)
  4. Only then draft the commit message.
Ralph Wiggum test at Articulation Closure

Walk every articulation deliverable. For each line item, ask: "Could an earnest follower-of-directions implement this without asking?" If yes, articulation is closed for that item. If no, the gap is named and closed before autonomous-loop execution can begin. The same bar applies to /goal conditions, Ralph loops, and any agentic implementation pattern. (§10)

8. What this view deliberately omits

  • Per-project application. the reference project, another project, Reflect, Journey — none of them appear here. That's by design; this view is the substrate, not the application.
  • The per-project orchestration HTML template. §32 establishes that every project will eventually receive a templated orchestration HTML that integrates every artifact into one navigable surface. Queued for authoring after methodology refinements settle and after the reference project Sprint 1 retrospective is complete. Per §39, the orchestration trajectory is HTML for solo-operator + AI; real software for multi-person + enterprise. The methodology website (publishing + onboarding + community) is a separate concern. §32 + §39 — not yet authored
  • Methodology family for other pillars. SAD v3 is Product-pillar / software product type. Brand variant and Business variant are tracked in methodology-family but not authored. The Sprint 1 retrospective will surface what these variants need to cover.
  • The detailed spec templates. Each spec document has a structure; that lives in SAD_SKILL_v3.md PART 6 and in the templates folder. Out of scope for this single-page view.
  • The decision protocols. Decision Boundary, Spec Change Classes 0–4, lifecycle regression protocol — referenced but not unpacked.
