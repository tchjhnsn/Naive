# AGENTS.md: naive

The map of this repo, loaded by every agent.

## What this is

Naive, the venture development framework, in its own repository (EE-118). It came out of tchjhnsn/everything-ecosystem with its history on 2026-11-05. That repository keeps what is not Naive: Mentura's console and platform library, the docs site, company docs and its own venture records, and it depends on Naive by version. Nothing here imports from it, and `node packages/naive/src/checks/check-boundary.mjs` fails on code that names a platform or console module. Code outside Naive imports it through the package's `exports` (`naive-framework/src/<unit>/<file>` for the code, and `naive-framework/<layer>/<file>` for the layer folders that have not moved yet), never by relative path. The package carries `packages/naive/lean/Naive/`, `packages/naive/src/terms/ontology-catalog.json` and the upgrade guides in `docs/upgrades/` so an app can check theorem names against it. TypeScript files ship as source until Naive publishes compiled JavaScript, and Node does not strip types under node_modules, so an app that imports a `.ts` file needs a loader until then. The code sits in `packages/naive/src/`, in units that import only the units before them: `core`, `records` (the record types, their schemas and the resolver), `terms` and `store`, `engine`, `checks`, `router`, then `interfaces` (EE-118 step 5). The root `package.json` stays the installable `naive-framework`, because a git dependency installs the repository root; `packages/naive/package.json` waits for registry publishing. The layer folders below empty into the 13 function modules in a later step.

The Everything Ecosystem methodology, packaged as one private repo (EE-001). Proposed genus: a venture development framework, in the same genus as web development frameworks (EE-024). Four layers (purpose, knowledge, operations, evidence) plus governance and interface. Knowledge is the memory layer where every record is stored, and the other layers define the records they write to it; SAD is no longer part of the system (EE-036). Operations is business operations (team, hiring, handoffs); execution folded into it, and MAD, the method for building software, left to be its own product (EE-038). A venture's scaffolding is a central data management structure: one place for everything the venture knows, with pointers to the systems that keep the rest. Naive is built for solo founders and small founding teams, for whom central data beats separate tools and gives agents the whole picture. It is not a software engineering framework: it leans toward a monorepo and asks only that the code be connected to the knowledge base, and it is opinionated about file conventions (EE-085).

## Build and test

- `node test.mjs` runs every test and check below and reports each one; CI runs it on every pull request (`.github/workflows/test.yml`). It needs Node 22.18 or later (developing only; the published package still runs on Node 20), `npm install` at the root (one root `package-lock.json`), and python3 with `jsonschema` for `packages/naive/src/records/validate.py`.
- `node packages/naive/src/checks/check-types.ts` (`npm run typecheck`) type-checks the code with `tsc` and `tsconfig.json` (`allowJs`, `checkJs`). Every file must be free of errors. `tsconfig.strict.json` holds `.ts` files to strict mode, and no file may carry an `@ts-` suppression.
- `node packages/naive/src/records/record-types.ts` writes `packages/naive/src/records/types/records.d.ts`, one TypeScript type per `packages/naive/src/records/*.schema.json` (`venture.schema.json` is `Venture`); `--check` fails when the committed file is stale, and a schema keyword or type name it cannot handle throws (`node packages/naive/src/records/record-types-test.ts`).
- `node evidence/skills/design-coverage/check.mjs --entity <dir>` checks design coverage for an entity.
- `node packages/naive/src/checks/check-ventures.mjs <dir>`, `node packages/naive/src/checks/check-nouns.mjs`, `node packages/naive/src/checks/check-integrations.mjs` check the schema's cross-file rules. `node packages/naive/src/checks/check-nouns.mjs --package <file> --function <id>` is the membership gate: one verdict for whether a handoff package's ontology belongs to that function (`--record` writes the sidecar). A rejection's disposition is read from the operating-rules module (`operations/operating-rules.json`, overlaid by a venture's own `operating-rules.json`). A schema checker that cannot run, or an operating-rules module that cannot be read, exits 2 and records nothing. A scoped noun `name@function` is owned by that function.
- `node packages/naive/src/checks/check-data-model.mjs` checks the data model and kit manifests (every JSON file has a record type, every skill one kit); `--md` prints the layer relationships derived from the kits (EE-018).
- `node packages/naive/src/checks/check-ready.mjs <venture dir> <handoff id>` checks a handoff is ready before anyone executes it (EE-019); `--record --by <who>` records it.
- `node packages/naive/src/checks/check-governance.mjs <dir>` checks ownership, boards, founder agreements and exits; `node packages/naive/src/engine/payouts.mjs <venture dir> [value]` computes who gets what in a sale (EE-022).
- `node packages/naive/src/checks/check-delegation.mjs [venture dir]` checks delegation (`governance/delegation.json`, template at `governance/venture-template/delegation.json`): no grant exceeds its grantor's, every chain reaches the founder, never-redelegated classes are not passed on, one-way doors are never delegated, expired grants fail, and no role template (`governance/venture-template/roles/<id>.json`) verifies itself. `packages/naive/src/checks/verify.mjs` holds the builder-is-not-verifier rule that `check-ready.mjs` and `check-execution.mjs` call (`node packages/naive/src/interfaces/tests/delegation-test.mjs`). The chief of staff agent is `agents/chief-of-staff/AGENTS.md`.
- `node packages/naive/src/checks/check-telos.mjs <dir>` checks each venture's telos (start with the end: every phase exit criterion traces to a measure).
- `node packages/naive/src/checks/check-publication.mjs <dir>` checks each venture's publication policy and every handoff that publishes: a named channel and content rule, and a person approving (EE-025).
- `node packages/naive/src/checks/check-validation.mjs <dir> [--json]` grades each venture's validation records from their cited evidence (high to very low, adapted from GRADE). The validation package is `packages/naive/library/packages/validation/` (EE-071). A kit, Mentura's enhanced package, is kept in Mentura and found through `NAIVE_KITS`.
- `node packages/naive/src/checks/check-execution.mjs <venture dir>` checks handoffs, evidence and decision rights; `node packages/naive/src/engine/run-handoff.mjs <venture dir> <handoff id>` runs a handoff's done-criteria and writes evidence (EE-017).
- `node packages/naive/src/interfaces/cli/naive.mjs typegen` writes `.naive/types/` from the route table and the MCP tools. `mentura typegen` is the same command. `naive upgrade <venture dir>` (was `mentura migrate`) runs the migrations in `packages/naive/src/engine/upgrades.json` up to the installed Naive and pins versions in `naive.config.json`; `--check`, `--guide`, `--adopt <package>`, `--canary`, `--agent` (a staged copy accepted with `--accept --confirm upgrade`) and `--framework` are in `packages/naive/src/engine/upgrade-venture.mjs` (`node packages/naive/src/engine/upgrades-test.mjs`). `mentura triggers` (`packages/naive/src/router/orchestration/triggers.mjs`) shows the triggers that run after each write and raises a failed run as a decision; `mentura notify` and `mentura stale` (`packages/naive/src/engine/stale.mjs`) mark summaries stale when a source changes; `mentura adapt` and `mentura adapters verify` (`packages/naive/src/interfaces/adapters.mjs`) write and test harness adapters. `naive port <folder> --venture <dir>` plans moving a folder into the venture whole and unchanged (to `repo/<name>` unless `--to` says where), naming what the move would break (worktrees, links into it, processes inside it); `--apply --confirm port` moves it with a rename, names it in `sources.json` as a read-only source of truth and logs the move in provenance (EE-076, a move since 2026-10-29; `node packages/naive/src/engine/port-test.mjs`). Each run writes `.release/port-trace.json`, which an app ships with `NAIVE_TRACE_CMD`. `naive migrate --from <project> --venture <dir>` has an agent rewrite the project as records, settled by `migrate-<function>` decisions and written through the router with `--apply` (`node packages/naive/src/engine/migrate-test.mjs`, with a stand-in agent). Neither opens a file that looks like a secret. `packages/naive/src/engine/init-venture.mjs` creates new ventures only. `node packages/naive/src/checks/check-private.mjs <dir>` fails when a private record or field could reach a model. `node packages/naive/src/engine/gate.mjs` is not a CLI: the gate reads `naive.config.json` and package `gate_rules`, matches the router's path patterns and never calls a model. `node packages/naive/src/checks/check-config.mjs <venture dir>` checks `naive.config.json` (`--explain <route>`, `--rules`, `--resolved`, `--pin`); `node packages/naive/src/engine/gate-drafts.mjs <venture dir> [--owner <role>]` lists held drafts; `node packages/naive/src/interfaces/tests/gate-test.mjs` tests the gate, the config, who is acting (`packages/naive/src/router/acting.mjs`) and access at the record.
- `node packages/naive/src/interfaces/cli/mentura.mjs <route> <action> --venture <id>` reads, writes, checks or runs one route; `node packages/naive/src/interfaces/mcp/server.mjs` is the MCP server and `node packages/naive/src/interfaces/api/server.mjs` the local API, all over `packages/naive/src/router/router.mjs` (EE-030). Routes follow the Next.js App Router (EE-032): `[id]` collection items, nested ventures by path, layout, view, not-found, loading and error, route groups by phase, the `system/overview` slots and team-plan robots; see `docs/reference/ROUTES.md`. `node packages/naive/src/interfaces/test.mjs` tests them. Records are read and written through connectors for the venture's sources (`packages/naive/src/store/connectors/`, EE-037); `node packages/naive/src/store/connectors/eval.mjs` runs the framework's (filesystem; its router, catalog and matrix evals are `node packages/naive/src/interfaces/tests/connectors-router-test.mjs`) against `packages/naive/src/store/connectors/suite.mjs`; an app adds its own connectors with `registerConnector` in `packages/naive/src/store/connectors/index.mjs`. The source map's `rules` are the source-of-truth matrix (EE-042, `packages/naive/src/store/connectors/resolve.mjs`): a system of record and owner per record type, attribute and context; `node packages/naive/src/checks/check-sources.mjs <dir>` refuses ties, and `node packages/naive/src/checks/check-where-used.mjs <dir>` reports where-used children that drifted from their parent. Every write through them appends to the venture's provenance log, `provenance.jsonl` (EE-031); `node packages/naive/src/checks/check-provenance.mjs <dir>` checks its hash chain, and `mentura baseline --venture <id>` adopts records written before the log. `node packages/naive/src/engine/need-now.mjs <venture dir>` says what a venture needs now (EE-028); `node packages/naive/src/engine/time-to-ready.mjs <venture dir>` measures time to running and ready; `node packages/naive/src/checks/check-team.mjs <dir>` checks team plans against the agent capability register (EE-029).
- `node packages/naive/src/engine/assess-problem.mjs <venture dir> [--as-is]` (route `purpose/validation/assess`) says what the problem's evidence is strong enough for: four assumptions labelled demonstrated to contradicted, the commitment they support (explore, prototype, charge, raise) and the next test, with no single score; it asks first when the record is incomplete (EE-050). `node packages/naive/src/engine/foundation.mjs <dir>` (route `purpose/foundation`) reports the strategic foundation by the Five Ws and How plus whether, and whose each is; `mentura confirm <statement>` and `mentura accept` of a foundation record need the name typed (EE-051).
- `node packages/naive/src/engine/freshness.mjs <venture dir>` (route `system/freshness`, `mentura freshness`) says which records are fresh, stale, expired or live holes: by time from freshness profiles (`knowledge/freshness.json`, overridden under `freshness` in `naive.config.json`, with per-phase profiles) and on demand when a dependency changed or a tag, path or package was revalidated (`mentura revalidate`, `verify`, `phase`; route `system/revalidate`). A stale record is still read, with a `freshness` flag; `--freeze <dir>` writes a shell that leaves live records as holes (Revalidating, V-1 to V-8; `node packages/naive/src/interfaces/tests/freshness-test.mjs`).
- `node packages/naive/src/checks/premise-lint.mjs <venture dir> [<route>] [--drafts] [--json] [--propose]` (`naive lint premises`) attacks the premises of a venture's goals, requirements, exit criteria, constraints and decisions. Questions are generated by formula from each record's fields and its graph, as state(record, field, aspect), with aspects undefined-term, unmeasurable, no-owner, unsupported-premise, orphan, conflict, dependency and phase-mismatch. Rules are off, warn (default) or error under `premise_lint.rules` in `naive.config.json`; it never edits a record, and `--propose` writes each finding as an open decision, and a rerun leaves a decision it already filed, or a person decided, as it is; measures are named `<goal>/<measure>`, and a bare measure id that two goals share is flagged (`node packages/naive/src/checks/premise-lint-test.mjs`).
- `node packages/naive/src/engine/decision-index.mjs <venture dir> [update|rebuild|read] [--since <iso>]` (route `system/decision-index`, `mentura index`) is the live decision index: the docket's ranking wrapped with structural impact for open decisions (`structural()` in `packages/naive/src/engine/impact.mjs`), phase weight, the requirement lift and violations from `foundation/requirements/*.json` when they exist; each run re-scores every active decision (an update equals a rebuild, so a passed due time re-ranks at once), caches in `.naive/decision-index.json` and appends rank history to `.naive/decision-index-history.jsonl` (`node packages/naive/src/interfaces/tests/decision-index-test.mjs`).
- The validation study (plugin beta first, Mentura later): interviews (`validation/interviews/[id]`), checkpoint feedback (`validation/feedback/[id]`) and bugs (`product/bugs/[id]`) are records; `node packages/naive/src/checks/check-validation-study.mjs <dir>` checks them across files and `naive bugs` (`packages/naive/src/engine/bugs.mjs`) lists open P0 and P1, the stable measure. The plugin beta's gate is `packages/naive/src/engine/beta-gate.mjs` over `beta/capabilities.json` (`naive beta status|feedback <capability>|unlock`): core (venture, docket, foundation) starts open, each later capability opens after feedback on the one before, unlock state is in `.naive/beta.json`, and the router refuses a locked route; it is on only with `beta.enabled` in `naive.config.json`. The tester is one id for the CLI and the router, `NAIVE_BETA_TESTER` (default `tester`), an anonymous id and never the acting role. `packages/naive/src/engine/feedback-route.mjs` routes feedback (Jev only when `beta.jev.send` is true, `beta.jev.set_by` names a person, `TYPESAFE_API_KEY` is set and a client is injected, accepted at 0.95, else a keyword fallback; no Jev client is built). `packages/naive/src/engine/telemetry.mjs` writes opt-in events (`packages/naive/src/records/telemetry.schema.json`, shared with Mentura) to `.naive/telemetry.jsonl`, which the router does not route, and sends only when `telemetry.send` is true and `telemetry.set_by` names a person; no sender is built. Feedback and interviews never enter a release (`NOT_SHIPPED` in `packages/naive/src/router/orchestration/releases.mjs`), even once a person confirms them. `node packages/naive/src/interfaces/tests/validation-study-test.mjs` tests it all.
- `node scripts/dependency-rules.ts` checks the monorepo's dependency rules: no new import cycle between units (a unit is a tracked top-level folder until the code moves into workspace packages) and one version per dependency, peer and optional ones included, across the root `package.json` and its workspaces. An import is a relative `import`, `export ... from` or `require` whose target file exists, so an example path inside a string or a comment is not one. Today's cycles are listed in `scripts/dependency-rules.json` and the list may only shrink; its `leaves` are folders that import nothing else in the repository (`packages/naive/src/records`). `--graph` prints the import graph. `node scripts/dependency-rules-test.ts` breaks each rule on a copy.
- Code reads the schema files and the data model through `packages/naive/src/records/index.mjs` (`schemaFile`, `readSchema`, `readDataModel`, `recordPath`, `recordsIn` for a copy of the repository). `node packages/naive/src/checks/check-record-paths.ts` fails when code elsewhere builds such a path from the folder name, or when `packages/naive/src/records/validate.py` disagrees with the resolver; `node packages/naive/src/checks/check-record-paths-test.ts` breaks it on copies.
- `node packages/naive/src/engine/bdd.mjs <file.feature>` runs Gherkin behaviors as tests, with step definitions in `<file>.steps.mjs`; behaviors are written first (EE-050).
- `node purpose/frameworks/product-anatomy/test.mjs` tests the Product Anatomy runner's role rules.
- `node packages/naive/src/checks/test.mjs` tests the checkers on broken copies; `python3 packages/naive/src/records/validate.py` validates every record against its schema.

## Docs

- The docs (docs/, every SKILL.md, and docs/master/naive-docs.md, exported from the master article) state only what is decided and built. Something not built says "not built" in that sentence.
- Ideas go through `naive capture`, not into the docs.
- READMEs are docs as code: each sits next to the code it describes, the code is the source of truth, and new ones follow `docs/readme-template.md`. READMEs link each other with relative links, which work on GitHub and in an editor.
- Every PR updates the docs or starts a line of its body with "No docs change: " and a real reason (a placeholder, a blank reason or the phrase quoted mid-line does not count); .github/workflows/docs-required.yml enforces it. Code here means any file that is not `.md` or `.mdx`, so JSON, CSV and images count. A PR that changes code under `packages/`, `schema/`, `interface/`, `packages/naive/library/packages/` or `purpose/` must update the README nearest that code, searched up to its top-level folder (`node packages/naive/src/checks/check-docs-claims.mjs --readmes` lists the ones owed). Only the docs `packages/naive/src/checks/check-docs-claims.mjs` scans count (`--scanned` lists them): `docs/master/*.md`, `packages/naive/library/packages/*/playbooks/*.md`, every SKILL.md and every README.md.
- `node packages/naive/src/checks/check-docs-claims.mjs` must pass: every command, flag, repository path and route the docs name exists in the code, and every relative Markdown link, inline or reference-style, resolves. HTML `href` and `src` are not checked.

## TypeScript

Naive is moving from JavaScript to TypeScript in four phases: type-check the JavaScript, generate record types from `packages/naive/src/records/*.schema.json`, rename modules to `.ts` folder by folder, then publish compiled JavaScript. Until that is done:

- New files are `.ts`. They run under Node's type stripping, so they use erasable syntax only: no `enum`, no `namespace`, no parameter properties (`erasableSyntaxOnly` in `tsconfig.json` enforces it). Import another `.ts` file by its `.ts` name.
- A record's type comes from its JSON Schema, never typed by hand.
- No `any` in new code. Use `unknown` and narrow it.
- Existing `.mjs` files are converted in their phase, not inside unrelated PRs.

## Rules

- Never read or print `.env*` files.
- Schema decisions are logged in `docs/decisions/decisions.json` and cited by id (`EE-NNN`). The schema never cites a decision from any instance.
- Torian merges. Agents open draft PRs and do not merge.

## Tooling

Every layer has `<layer>/tooling/integrations.json`: the tools and services it can use, each checked against `packages/naive/src/records/integration.schema.json` (status in-use, candidate or rejected; interfaces such as files, MCP, API, SDK; credentials by variable name only). Agent runtimes (Claude Agent SDK, Cursor Agent SDK) are listed under `execution/tooling/`. The interface layer is narrower: an interface lets a person, with agents, work across at least three of the five other layers in one session. Agent harnesses (Claude Code, Cursor, Codex) are the default kind; the operator console is a custom one. A tool serving one or two layers (Obsidian, Linear) is an integration of those layers. `node packages/naive/src/checks/check-integrations.mjs` enforces this.

Choosing tools is opt-in: when someone wants help, `operations/skills/tool-selection/SKILL.md` gives the principles for the questions and the scoring (Jev plus a reasoning model), and each layer's `tooling/questions.md` gives its dimensions and example questions. Knowledge has one so far.

## Ventures

The ecosystem is a schema; a workspace is an instance made of ventures (EE-002, EE-011). A venture is anything a builder undertakes, at a phase from Discovery to Platform (EE-012); personal life is out of scope (EE-009). Each venture has a `venture.json` (`packages/naive/src/records/venture.schema.json`), product cards in `products/`, account records in `accounts/` where it keeps them (EE-021), and the three pillars. Create one with `node packages/naive/src/engine/init-venture.mjs`; check a workspace with `node packages/naive/src/checks/check-ventures.mjs <dir>`. Work in a venture runs as handoffs (`execution/handoffs/`), proved by evidence (`evidence/results/`), under its decision rights (`governance/decision-rights.json`). The example ventures are in `packages/naive/src/records/examples/` (`packages/naive/src/records/examples/workspace/` and `packages/naive/src/records/examples/software/`); real ventures live in their tenants' own stores, outside this repository. Every record type is indexed in `packages/naive/src/engine/README.md` and listed, with its owning layer, in `packages/naive/src/records/data-model.json`. Each layer's manifest (skills, records it still owns, reads and writes) is in `<layer>/layer.json`. Venture packages are `packages/naive/library/packages/<name>/package.json`. A kit is Mentura's enhanced package, kept in Mentura and found through `NAIVE_KITS` (EE-071). See `docs/design/LAYERS_AND_KITS_2026-10-27.md`. Design: `docs/design/VENTURES_2026-10-27.md`.

## Nouns and references

Standards first (EE-014): use an established term with its standard meaning, and coin one only when none exists. `packages/naive/src/terms/ontology.json` is canonical for nouns (`packages/naive/src/terms/ontology.md` is its readable form); `node packages/naive/src/checks/check-nouns.mjs` fails when a retired noun reappears, when a noun has no standard, or when a function's capabilities are not nouns it owns. Each noun names its function, or null when the word is shared. Each layer keeps the sources behind its defaults in `<layer>/references/references.json`; `knowledge/skills/find-reference/` fills and re-checks them.
