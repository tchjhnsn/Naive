# AGENTS.md: naive

The map of this repo, loaded by every agent.

## What this is

Naive, the venture development framework, in its own repository (EE-118). It came out of tchjhnsn/everything-ecosystem with its history on 2026-11-05. That repository keeps what is not Naive: Mentura's console and platform library, the docs site, company docs and its own venture records, and it depends on Naive by version. Nothing here imports from it, and `node packages/naive/src/checks/check-boundary.ts` fails on code that names a platform or console module. Code outside Naive imports it through the package's `exports` (`naive-framework/src/<unit>/<file>`, the function modules included as `naive-framework/src/functions/<function>/...`, and the venture template as `naive-framework/template/...`), never by relative path. The package carries `packages/naive/lean/Naive/`, `packages/naive/src/terms/ontology-catalog.json` and the upgrade guides in `docs/upgrades/` so an app can check theorem names against it. Node does not strip types under node_modules, so the package ships compiled JavaScript in `dist/` and its `exports` and `bin` point there (EE-159): an app imports `naive-framework/src/terms/engine.ts` or `naive-framework/src/terms/engine.mjs` and gets the compiled `.mjs`, with no loader. The source ships beside it, and each export's `types` condition names the source file, so an import by its `.mjs` name is typed from the `.ts` source. The code sits in `packages/naive/src/`, in units that import only the units before them: `core`, `records` (the record types, their schemas and the resolver), `terms` and `store`, `engine`, `checks`, `router`, then `interfaces` (EE-118 step 5). The root `package.json` stays the installable `naive-framework`, because a git dependency installs the repository root; `packages/naive/package.json` waits for registry publishing. The six layer folders emptied into the 13 function modules in step 7.

The Everything Ecosystem methodology, packaged as one private repo (EE-001). Proposed genus: a venture development framework, in the same genus as web development frameworks (EE-024). Four layers (purpose, knowledge, operations, evidence) plus governance and interface. Knowledge is the memory layer where every record is stored, and the other layers define the records they write to it; SAD is no longer part of the system (EE-036). Operations is business operations (team, hiring, handoffs); execution folded into it, and MAD, the method for building software, left to be its own product (EE-038). A venture's scaffolding is a central data management structure: one place for everything the venture knows, with pointers to the systems that keep the rest. Naive is built for solo founders and small founding teams, for whom central data beats separate tools and gives agents the whole picture. It is not a software engineering framework: it leans toward a monorepo and asks only that the code be connected to the knowledge base, and it is opinionated about file conventions (EE-085).

## Build and test

- `node test.ts` runs every test and check below and reports each one; CI runs it on every pull request (`.github/workflows/test.yml`). It needs Node 22.19 or later, the floor for Naive and every venture since Effect 4 requires it (EE-158), `npm install` at the root (one root `package-lock.json`), and, for one cross-check only, python3 with `jsonschema`: `node packages/naive/src/records/validate-test.ts` compares `packages/naive/src/records/validate.ts` with jsonschema and skips without it. Naive validates records in process with `validate.ts` and needs no Python.
- `node scripts/build.ts` (`npm run build`, and npm's `prepare`, so a git dependency builds on install) writes `dist/`, the compiled package (EE-159): every file `npm pack` lists from the `files` field, less `packages/naive/test/`, at its own path (npm 11 lists a UUID in a file name as `***`, so such a path is matched to the real file in its folder), with each `.ts` and `.mjs` outside `fixtures/` compiled by tsc (`noCheck`, `rewriteRelativeImportExtensions`; declaration files and `*.recipe.ts` are data and are copied) and every other file copied, so a module finds its JSON, templates and scripts by the same relative path. A string literal that names a compiled `.ts` file by its path from the file or the package root becomes `.mjs`, and so does a whole JSON string that names one from the package root (a connector's or a migration's `module`), a relative import that names no file in `dist/` fails the build, and a build whose inputs match `dist/.build-stamp` does nothing. `dist/` is gitignored, and the repository's own tests and CLIs run the source. `node scripts/build-test.ts` tests the build; the packed-install tests in `packages/naive/src/engine/workspace-init-test.ts` and `packages/create-venture/test.ts` install the packed package and run it with type stripping off.
- The docs site: `npm ci` at the root, then `npm ci`, `npm run check:content` and `npm run build` in `site/`; CI's `site` job also runs the site's own tests (`site/AGENTS.md`). The type gate and lint leave `site/` to its own Next.js build.
- `node packages/naive/src/checks/check-types.ts` (`npm run typecheck`) type-checks the code with `tsc` and `tsconfig.json` (`allowJs`, `checkJs`). Every file must be free of errors. `tsconfig.strict.json` holds `.ts` files to strict mode, and no file may carry an `@ts-` suppression.
- `node packages/naive/src/records/record-types.ts` writes `packages/naive/src/records/types/records.d.ts`, one TypeScript type per `packages/naive/src/records/*.schema.json` (`venture.schema.json` is `Venture`); `--check` fails when the committed file is stale, and a schema keyword or type name it cannot handle throws (`node packages/naive/src/records/record-types-test.ts`).
- `node packages/naive/src/functions/capabilities/skills/design-coverage/check.ts --entity <dir>` checks design coverage for an entity.
- `node packages/naive/src/checks/check-ventures.ts <dir>`, `node packages/naive/src/checks/check-nouns.ts`, `node packages/naive/src/checks/check-integrations.ts` check the schema's cross-file rules. `node packages/naive/src/checks/check-nouns.ts --package <file> --function <id>` is the membership gate: one verdict for whether a handoff package's ontology belongs to that function (`--record` writes the sidecar). A rejection's disposition is read from the operating-rules module (`packages/naive/src/terms/operating-rules.json`, overlaid by a venture's own `operating-rules.json`). A schema checker that cannot run, or an operating-rules module that cannot be read, exits 2 and records nothing. A scoped noun `name@function` is owned by that function.
- `node packages/naive/src/checks/check-data-model.ts` checks the data model and kit manifests (every JSON file has a record type, every skill one kit, every file in an example venture a kind: record, log or derived, every record type a `function` that is a `packages/naive/src/functions/departments.json` id or null and agrees with `PACKAGE_FUNCTION`, every workspace and venture record type a `data` category, master, reference, transactional or derived, with a log held to transactional (EE-184)); `--md` prints the layer relationships derived from the kits (EE-018).
- `node packages/naive/src/checks/check-ready.ts <venture dir> <handoff id>` checks a handoff is ready before anyone executes it (EE-019); `--record --by <who>` records it.
- `node packages/naive/src/checks/check-governance.ts <dir>` checks ownership, boards, founder agreements and exits; `node packages/naive/src/engine/payouts.ts <venture dir> [value]` computes who gets what in a sale (EE-022).
- `node packages/naive/src/checks/check-delegation.ts [venture dir]` checks delegation (`governance/delegation.json`, template at `packages/naive/template/governance/delegation.json`): no grant exceeds its grantor's, every chain reaches the founder, never-redelegated classes are not passed on, one-way doors are never delegated, expired grants fail, every role template's `function` is a departments.json id (or `all` for the founder alone), and no role template (`packages/naive/template/governance/roles/<id>.json`) verifies itself. `packages/naive/src/checks/verify.ts` holds the builder-is-not-verifier rule that `check-ready.ts` and `check-execution.ts` call (`node packages/naive/src/interfaces/tests/delegation-test.ts`). The chief of staff agent is `agents/chief-of-staff/AGENTS.md`.
- `node packages/naive/src/checks/check-telos.ts <dir>` checks each venture's telos (start with the end: every phase exit criterion traces to a measure).
- `node packages/naive/src/checks/check-publication.ts <dir>` checks each venture's publication policy and every handoff that publishes: a named channel and content rule, and a person approving (EE-025).
- `naive publish check` (`packages/naive/src/engine/publish-lint.ts`) lints the copy a record holds as well as a page's prose (EE-214): `packages/naive/src/engine/record-copy.ts` gives it each marketing sitemap section's `draft_copy` and every string under a field the visibility sidecar calls public, so a word published from a record meets the same stages. A mark is matched case-insensitively and on word boundaries, and a name marked `private` is an error whatever its rule's severity, which stays a prior under `publish_lint.rules` in `naive.config.json`. The marketing and sales function writes its own marks in `marketing/publish-terms.json` (route `marketing/publish-terms`, `packages/naive/src/records/publish-terms.schema.json`), names only and never severities or waivers, so the role that owns the words can tighten the gate and never loosen it. The config is read through `configFile` in `packages/naive/src/core/venture-paths.ts`, so a structured venture's `meta/naive.config.json` counts (`node packages/naive/src/engine/publish-lint-test.ts`).
- `node packages/naive/src/checks/check-validation.ts <dir> [--json]` grades each venture's validation records from their cited evidence (high to very low, adapted from GRADE). The validation package is `packages/naive/library/packages/validation/` (EE-071). A kit, Mentura's enhanced package, is kept in Mentura and found through `NAIVE_KITS`.
- `node packages/naive/src/checks/check-execution.ts <venture dir>` checks handoffs, evidence and decision rights; `node packages/naive/src/engine/run-handoff.ts <venture dir> <handoff id>` runs a handoff's done-criteria and writes evidence (EE-017). A bash criterion runs with `NAIVE_VENTURE` set to the business folder, and the function workflows' `records-valid` is `node packages/naive/src/checks/check-records.ts "$NAIVE_VENTURE"`, which validates that business's records against their schemas (`node packages/naive/src/checks/check-records-test.ts`).
- `node packages/naive/src/interfaces/cli/naive.ts typegen` writes `.naive/types/` from the route table and the MCP tools. `mentura typegen` is the same command. `naive upgrade <venture dir>` (was `mentura migrate`) runs the migrations in `packages/naive/src/engine/upgrades.json` up to the installed Naive and pins versions in `naive.config.json`; `--check`, `--guide`, `--adopt <package>`, `--canary`, `--agent` (a staged copy accepted with `--accept --confirm upgrade`) and `--framework` are in `packages/naive/src/engine/upgrade-venture.ts` (`node packages/naive/src/engine/upgrades-test.ts`). `naive upgrade <venture dir> --layout src` moves a venture onto the src layout (EE-118 step 8): each package folder under `src/<function>/`, static files in `public/`, and every logical path unchanged; `init-venture.ts --layout src` starts one there from `packages/naive/template/` (`node packages/naive/src/engine/src-layout-test.ts`). `mentura triggers` (`packages/naive/src/router/orchestration/triggers.ts`) shows the triggers that run after each write and raises a failed run as a decision, and runs each trigger once per event across a crash (EE-161, `node packages/naive/src/interfaces/tests/durable-triggers-test.ts`); `mentura notify` and `mentura stale` (`packages/naive/src/engine/stale.ts`) mark summaries stale when a source changes; `mentura adapt` and `mentura adapters verify` (`packages/naive/src/interfaces/adapters.ts`) write and test harness adapters. `naive port <folder> --venture <dir>` plans moving a folder into the venture whole and unchanged (to `repo/<name>` unless `--to` says where), naming what the move would break (worktrees, links into it, processes inside it); `--apply --confirm port` moves it with a rename, names it in `sources.json` as a read-only source of truth and logs the move in provenance (EE-076, a move since 2026-10-29; `node packages/naive/src/engine/port-test.ts`). Each run writes `.release/port-trace.json`, which an app ships with `NAIVE_TRACE_CMD`. `naive migrate --from <project> --venture <dir>` has an agent rewrite the project as records, settled by `migrate-<function>` decisions and written through the router with `--apply` (`node packages/naive/src/engine/migrate-test.ts`, with a stand-in agent). Neither opens a file that looks like a secret. `packages/naive/src/engine/init-venture.ts` creates new ventures only. `node packages/naive/src/checks/check-private.ts <dir>` fails when a private record or field could reach a model. `node packages/naive/src/engine/gate.ts` is not a CLI: the gate reads `naive.config.json` and package `gate_rules`, matches the router's path patterns and never calls a model. `node packages/naive/src/checks/check-config.ts <venture dir>` checks `naive.config.json` (`--explain <route>`, `--rules`, `--resolved`, `--pin`); `node packages/naive/src/engine/gate-drafts.ts <venture dir> [--owner <role>]` lists held drafts; `node packages/naive/src/interfaces/tests/gate-test.ts` tests the gate, the config, who is acting (`packages/naive/src/router/acting.ts`) and access at the record. One writer per file (signal library build item 4): a record type with `writer: "projection"` in the data model is written only by the signal projector (`asProjector` in `packages/naive/src/router/acting.ts`, a symbol no JSON carries), and every other actor, a person included, is refused before the schema with the hint to emit a superseding signal (`naive signals emit`, not built); the projector creates a record a person owns only when it is missing (`writerRule` in `packages/naive/src/engine/gate.ts`, `node packages/naive/src/interfaces/tests/projector-test.ts`).

Records are read and written through connectors for the venture's sources (`packages/naive/src/store/connectors/`, EE-037); `node packages/naive/src/store/connectors/eval.ts` runs the framework's (filesystem; its router, catalog and matrix evals are `node packages/naive/src/interfaces/tests/connectors-router-test.ts`) against `packages/naive/src/store/connectors/suite.ts`; an app adds its own connectors with `registerConnector` in `packages/naive/src/store/connectors/index.ts`. Every write through them appends to the venture's provenance log, `provenance.jsonl` (EE-031); `node packages/naive/src/checks/check-provenance.ts <dir>` checks its hash chain, and `mentura baseline --venture <id>` adopts records written before the log. `node packages/naive/src/engine/need-now.ts <venture dir>` says what a venture needs now (EE-028); `node packages/naive/src/engine/time-to-ready.ts <venture dir>` measures time to running and ready; `node packages/naive/src/checks/check-team.ts <dir>` checks team plans against the agent capability register (EE-029). - `node packages/naive/src/engine/freshness.ts <venture dir>` (route `system/freshness`, `mentura freshness`) says which records are fresh, stale, expired or live holes: by time from freshness profiles (`packages/naive/src/engine/freshness.json`, overridden under `freshness` in `naive.config.json`, with per-phase profiles) and on demand when a dependency changed or a tag, path or package was revalidated (`mentura revalidate`, `verify`, `phase`; route `system/revalidate`). A stale record is still read, with a `freshness` flag; `--freeze <dir>` writes a shell that leaves live records as holes (Revalidating, V-1 to V-8; `node packages/naive/src/interfaces/tests/freshness-test.ts`).

Rules are off, warn (default) or error under `premise_lint.rules` in `naive.config.json`; it never edits a record, and `--propose` writes each finding as an open decision, and a rerun leaves a decision it already filed, or a person decided, as it is; measures are named `<goal>/<measure>`, and a bare measure id that two goals share is flagged (`node packages/naive/src/checks/premise-lint-test.ts`).

- READMEs are docs as code: each sits next to the code it describes, the code is the source of truth, and new ones follow `docs/readme-template.md`. READMEs link each other with relative links, which work on GitHub and in an editor.
- Every PR updates the docs or starts a line of its body with "No docs change: " and a real reason (a placeholder, a blank reason or the phrase quoted mid-line does not count); .github/workflows/docs-required.yml enforces it. Code here means any file that is not `.md` or `.mdx`, so JSON, CSV and images count. A PR that changes code under `packages/`, `schema/`, `interface/`, `packages/naive/library/packages/` or `purpose/` must update the README nearest that code, searched up to its top-level folder (`node packages/naive/src/checks/check-docs-claims.ts --readmes` lists the ones owed). Only the docs `packages/naive/src/checks/check-docs-claims.ts` scans count (`--scanned` lists them): `docs/master/*.md`, `packages/naive/library/packages/*/playbooks/*.md`, every SKILL.md and every README.md.
- `node packages/naive/src/checks/check-docs-claims.ts` must pass: every command, flag, repository path and route the docs name exists in the code, and every relative Markdown link, inline or reference-style, resolves. HTML `href` and `src` are not checked.

## TypeScript

Naive is moving from JavaScript to TypeScript in four phases (EE-087): type-check the JavaScript, generate record types from `packages/naive/src/records/*.schema.json`, rename modules to `.ts` folder by folder, and publish compiled JavaScript. The last phase is done (EE-159): the package ships `dist/`, so a module an app or a venture reaches from node_modules may be `.ts`. Until the renaming is done:

- New files are `.ts`, with no exception, including modules the router, `init-venture`, `create-venture` and the CLIs import. They run under Node's type stripping in the repository, so they use erasable syntax only: no `enum`, no `namespace`, no parameter properties (`erasableSyntaxOnly` in `tsconfig.json` enforces it). Import another `.ts` file by its `.ts` name. Code that runs a `.ts` script by path names it by its `.ts` path as a string literal or through `naiveScript`, so the compiled copy runs the `.mjs`. Every compiled file is `.mjs` (`scripts/build.ts`), so a module converted from `.mjs` to `.ts` keeps the path an app imports it by.
- A record's type comes from its JSON Schema, never typed by hand.
- No `any` in new code. Use `unknown` and narrow it.
- Existing `.mjs` files are converted unit by unit, not inside unrelated PRs. `node scripts/to-ts.ts <file.mjs>...` renames them with git mv and rewrites every reference in the repository (`node scripts/to-ts-test.ts`); typing them under `tsconfig.strict.json` is the converter's work.

## Vendored repositories

`repos/` holds the source of libraries Naive depends on, added with `git subtree --squash` so agents can read the real code, its tests and its docs instead of guessing from the web or from compiled `node_modules`. `repos/effect` is Effect at the tag of the exact version in `package.json` (`effect@4.1.5`).

- Read `repos/effect/LLMS.md` before writing Effect code, and use `repos/effect/packages/effect/src` and its tests as the source of truth for idiomatic usage and API design.
- Use vendored repositories as read-only reference. Prefer their examples and patterns over generated guesses or web search results.
- Do not edit files under `repos/` unless asked.
- Do not import from `repos/`. Code imports the installed package (`effect`), never the vendored copy.
- A vendored copy moves with its pin, in the same pull request: `git subtree pull --prefix=repos/effect https://github.com/Effect-TS/effect.git effect@<version> --squash`. `node scripts/vendored.ts` fails when they differ (`node scripts/vendored-test.ts`).
- `repos/` is not shipped in the package and is left out of the type check, ESLint, the docs claims check, the boundary check and the data model check.

## Rules

- Never read or print `.env*` files.
- Schema decisions are logged in `docs/decisions/decisions.json` and cited by id (`EE-NNN`). The schema never cites a decision from any instance.
- Torian merges. Agents open draft PRs and do not merge.

## Tooling

Every layer has `packages/naive/src/records/layers/<layer>/tooling/integrations.json`: the tools and services it can use, each checked against `packages/naive/src/records/integration.schema.json` (status in-use, candidate or rejected; interfaces such as files, MCP, API, SDK; credentials by variable name only). Agent runtimes (Claude Agent SDK, Cursor Agent SDK) are listed under `execution/tooling/`. The interface layer is narrower: an interface lets a person, with agents, work across at least three of the five other layers in one session. Agent harnesses (Claude Code, Cursor, Codex) are the default kind; the operator console is a custom one. A tool serving one or two layers (Obsidian, Linear) is an integration of those layers. `node packages/naive/src/checks/check-integrations.ts` enforces this.

Choosing tools is opt-in: when someone wants help, `packages/naive/src/functions/it/skills/tool-selection/SKILL.md` gives the principles for the questions and the scoring (Jev plus a reasoning model), and each layer's `tooling/questions.md` gives its dimensions and example questions. Knowledge has one so far.

## Ventures

The ecosystem is a schema; a workspace is an instance made of ventures (EE-002, EE-011). A venture is anything a builder undertakes, at a phase from Discovery to Platform (EE-012); personal life is out of scope (EE-009). Each venture has a `venture.json` (`packages/naive/src/records/venture.schema.json`), product cards in `products/`, account records in `accounts/` where it keeps them (EE-021), and the three pillars. Create one with `node packages/naive/src/engine/init-venture.ts`; check a workspace with `node packages/naive/src/checks/check-ventures.ts <dir>`. Work in a venture runs as handoffs (`execution/handoffs/`), proved by evidence (`evidence/results/`), under its decision rights (`governance/decision-rights.json`). The example ventures are in `packages/naive/src/records/examples/` (`packages/naive/src/records/examples/workspace/` and `packages/naive/src/records/examples/software/`); real ventures live in their tenants' own stores, outside this repository. Every record type is indexed in `packages/naive/src/engine/README.md` and listed, with its owning layer, in `packages/naive/src/records/data-model.json`. Each layer's manifest (skills, records it still owns, reads and writes) is in `packages/naive/src/records/layers/<layer>/layer.json`. Venture packages are `packages/naive/library/packages/<name>/package.json`. A kit is Mentura's enhanced package, kept in Mentura and found through `NAIVE_KITS` (EE-071). See `docs/design/LAYERS_AND_KITS_2026-10-27.md`. Design: `docs/design/VENTURES_2026-10-27.md`.

## Nouns and references

Standards first (EE-014): use an established term with its standard meaning, and coin one only when none exists. `packages/naive/src/terms/ontology.json` is canonical for nouns (`packages/naive/src/terms/ontology.md` is its readable form); `node packages/naive/src/checks/check-nouns.ts` fails when a retired noun reappears, when a noun has no standard, or when a function's capabilities are not nouns it owns. Each noun names its function, or null when the word is shared. Each layer keeps the sources behind its defaults in `packages/naive/src/records/layers/<layer>/references/references.json`; `packages/naive/src/functions/capabilities/skills/find-reference/` fills and re-checks them.
