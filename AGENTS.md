# AGENTS.md: naive

The map of this repo, loaded by every agent.

## What this is

Naive, the venture development framework, in its own repository (EE-118). It came out of tchjhnsn/everything-ecosystem with its history on 2026-11-05. That repository keeps what is not Naive: Mentura's console and platform library, the docs site, company docs and its own venture records, and it depends on Naive by version. Nothing here imports from it, and `node packages/naive/src/checks/check-boundary.mjs` fails on code that names a platform or console module. Code outside Naive imports it through the package's `exports` (`naive-framework/src/<unit>/<file>`, the function modules included as `naive-framework/src/functions/<function>/...`, and the venture template as `naive-framework/template/...`), never by relative path. The package carries `packages/naive/lean/Naive/`, `packages/naive/src/terms/ontology-catalog.json` and the upgrade guides in `docs/upgrades/` so an app can check theorem names against it. TypeScript files ship as source until Naive publishes compiled JavaScript, and Node does not strip types under node_modules, so an app that imports a `.ts` file needs a loader until then. The code sits in `packages/naive/src/`, in units that import only the units before them: `core`, `records` (the record types, their schemas and the resolver), `terms` and `store`, `engine`, `checks`, `router`, then `interfaces` (EE-118 step 5). The root `package.json` stays the installable `naive-framework`, because a git dependency installs the repository root; `packages/naive/package.json` waits for registry publishing. The six layer folders emptied into the 13 function modules in step 7.

The Everything Ecosystem methodology, packaged as one private repo (EE-001). Proposed genus: a venture development framework, in the same genus as web development frameworks (EE-024). Four layers (purpose, knowledge, operations, evidence) plus governance and interface. Knowledge is the memory layer where every record is stored, and the other layers define the records they write to it; SAD is no longer part of the system (EE-036). Operations is business operations (team, hiring, handoffs); execution folded into it, and MAD, the method for building software, left to be its own product (EE-038). A venture's scaffolding is a central data management structure: one place for everything the venture knows, with pointers to the systems that keep the rest. Naive is built for solo founders and small founding teams, for whom central data beats separate tools and gives agents the whole picture. It is not a software engineering framework: it leans toward a monorepo and asks only that the code be connected to the knowledge base, and it is opinionated about file conventions (EE-085).

## Build and test

- `node test.mjs` runs every test and check below and reports each one; CI runs it on every pull request (`.github/workflows/test.yml`). It needs Node 22.18 or later (developing only; the published package still runs on Node 20), `npm install` at the root (one root `package-lock.json`), and, for one cross-check only, python3 with `jsonschema`: `node packages/naive/src/records/validate-test.ts` compares `packages/naive/src/records/validate.mjs` with jsonschema and skips without it. Naive validates records in process with `validate.mjs` and needs no Python.
- `node packages/naive/src/checks/check-types.ts` (`npm run typecheck`) type-checks the code with `tsc` and `tsconfig.json` (`allowJs`, `checkJs`). Every file must be free of errors. `tsconfig.strict.json` holds `.ts` files to strict mode, and no file may carry an `@ts-` suppression.
- `node packages/naive/src/records/record-types.ts` writes `packages/naive/src/records/types/records.d.ts`, one TypeScript type per `packages/naive/src/records/*.schema.json` (`venture.schema.json` is `Venture`); `--check` fails when the committed file is stale, and a schema keyword or type name it cannot handle throws (`node packages/naive/src/records/record-types-test.ts`).
- `node packages/naive/src/functions/capabilities/skills/design-coverage/check.mjs --entity <dir>` checks design coverage for an entity.
- `node packages/naive/src/checks/check-ventures.mjs <dir>`, `node packages/naive/src/checks/check-nouns.mjs`, `node packages/naive/src/checks/check-integrations.mjs` check the schema's cross-file rules. `node packages/naive/src/checks/check-nouns.mjs --package <file> --function <id>` is the membership gate: one verdict for whether a handoff package's ontology belongs to that function (`--record` writes the sidecar). A rejection's disposition is read from the operating-rules module (`packages/naive/src/terms/operating-rules.json`, overlaid by a venture's own `operating-rules.json`). A schema checker that cannot run, or an operating-rules module that cannot be read, exits 2 and records nothing. A scoped noun `name@function` is owned by that function.
- `node packages/naive/src/checks/check-data-model.mjs` checks the data model and kit manifests (every JSON file has a record type, every skill one kit, every file in an example venture a kind: record, log or derived); `--md` prints the layer relationships derived from the kits (EE-018).
- `node packages/naive/src/checks/check-ready.mjs <venture dir> <handoff id>` checks a handoff is ready before anyone executes it (EE-019); `--record --by <who>` records it.
- `node packages/naive/src/checks/check-governance.mjs <dir>` checks ownership, boards, founder agreements and exits; `node packages/naive/src/engine/payouts.mjs <venture dir> [value]` computes who gets what in a sale (EE-022).
- `node packages/naive/src/checks/check-delegation.mjs [venture dir]` checks delegation (`governance/delegation.json`, template at `packages/naive/template/governance/delegation.json`): no grant exceeds its grantor's, every chain reaches the founder, never-redelegated classes are not passed on, one-way doors are never delegated, expired grants fail, and no role template (`packages/naive/template/governance/roles/<id>.json`) verifies itself. `packages/naive/src/checks/verify.mjs` holds the builder-is-not-verifier rule that `check-ready.mjs` and `check-execution.mjs` call (`node packages/naive/src/interfaces/tests/delegation-test.mjs`). The chief of staff agent is `agents/chief-of-staff/AGENTS.md`.
- `node packages/naive/src/checks/check-telos.mjs <dir>` checks each venture's telos (start with the end: every phase exit criterion traces to a measure).
- `node packages/naive/src/checks/check-publication.mjs <dir>` checks each venture's publication policy and every handoff that publishes: a named channel and content rule, and a person approving (EE-025).
- `node packages/naive/src/checks/check-validation.mjs <dir> [--json]` grades each venture's validation records from their cited evidence (high to very low, adapted from GRADE). The validation package is `packages/naive/library/packages/validation/` (EE-071). A kit, Mentura's enhanced package, is kept in Mentura and found through `NAIVE_KITS`.
- `node packages/naive/src/checks/check-execution.mjs <venture dir>` checks handoffs, evidence and decision rights; `node packages/naive/src/engine/run-handoff.mjs <venture dir> <handoff id>` runs a handoff's done-criteria and writes evidence (EE-017).
- `node packages/naive/src/interfaces/cli/naive.mjs typegen` writes `.naive/types/` from the route table and the MCP tools. `mentura typegen` is the same command. `naive upgrade <venture dir>` (was `mentura migrate`) runs the migrations in `packages/naive/src/engine/upgrades.json` up to the installed Naive and pins versions in `naive.config.json`; `--check`, `--guide`, `--adopt <package>`, `--canary`, `--agent` (a staged copy accepted with `--accept --confirm upgrade`) and `--framework` are in `packages/naive/src/engine/upgrade-venture.mjs` (`node packages/naive/src/engine/upgrades-test.mjs`). `naive upgrade <venture dir> --layout src` moves a venture onto the src layout (EE-118 step 8): each package folder under `src/<function>/`, static files in `public/`, and every logical path unchanged; `init-venture.mjs --layout src` starts one there from `packages/naive/template/` (`node packages/naive/src/engine/src-layout-test.mjs`). `mentura triggers` (`packages/naive/src/router/orchestration/triggers.mjs`) shows the triggers that run after each write and raises a failed run as a decision; `mentura notify` and `mentura stale` (`packages/naive/src/engine/stale.mjs`) mark summaries stale when a source changes; `mentura adapt` and `mentura adapters verify` (`packages/naive/src/interfaces/adapters.mjs`) write and test harness adapters. `naive port <folder> --venture <dir>` plans moving a folder into the venture whole and unchanged (to `repo/<name>` unless `--to` says where), naming what the move would break (worktrees, links into it, processes inside it); `--apply --confirm port` moves it with a rename, names it in `sources.json` as a read-only source of truth and logs the move in provenance (EE-076, a move since 2026-10-29; `node packages/naive/src/engine/port-test.mjs`). Each run writes `.release/port-trace.json`, which an app ships with `NAIVE_TRACE_CMD`. `naive migrate --from <project> --venture <dir>` has an agent rewrite the project as records, settled by `migrate-<function>` decisions and written through the router with `--apply` (`node packages/naive/src/engine/migrate-test.mjs`, with a stand-in agent). Neither opens a file that looks like a secret. `packages/naive/src/engine/init-venture.mjs` creates new ventures only. `node packages/naive/src/checks/check-private.mjs <dir>` fails when a private record or field could reach a model. `node packages/naive/src/engine/gate.mjs` is not a CLI: the gate reads `naive.config.json` and package `gate_rules`, matches the router's path patterns and never calls a model. `node packages/naive/src/checks/check-config.mjs <venture dir>` checks `naive.config.json` (`--explain <route>`, `--rules`, `--resolved`, `--pin`); `node packages/naive/src/engine/gate-drafts.mjs <venture dir> [--owner <role>]` lists held drafts; `node packages/naive/src/interfaces/tests/gate-test.mjs` tests the gate, the config, who is acting (`packages/naive/src/router/acting.mjs`) and access at the record. One writer per file (signal library build item 4): a record type with `writer: "projection"` in the data model is written only by the signal projector (`asProjector` in `packages/naive/src/router/acting.mjs`, a symbol no JSON carries), and every other actor, a person included, is refused before the schema with the hint to emit a superseding signal (`naive signals emit`, not built); the projector creates a record a person owns only when it is missing (`writerRule` in `packages/naive/src/engine/gate.mjs`, `node packages/naive/src/interfaces/tests/projector-test.ts`).
- `node packages/naive/src/interfaces/cli/mentura.mjs <route> <action> --venture <id>` reads, writes, checks or runs one route; `node packages/naive/src/interfaces/mcp/server.mjs` is the MCP server and `node packages/naive/src/interfaces/api/server.mjs` the local API, all over `packages/naive/src/router/router.mjs` (EE-030). Routes follow the Next.js App Router (EE-032): `[id]` collection items, nested ventures by path, layout, view, not-found, loading and error, route groups by phase, the `system/overview` slots and team-plan robots; see `docs/reference/ROUTES.md`. `node packages/naive/src/interfaces/test.mjs` tests them. Records are read and written through connectors for the venture's sources (`packages/naive/src/store/connectors/`, EE-037); `node packages/naive/src/store/connectors/eval.mjs` runs the framework's (filesystem; its router, catalog and matrix evals are `node packages/naive/src/interfaces/tests/connectors-router-test.mjs`) against `packages/naive/src/store/connectors/suite.mjs`; an app adds its own connectors with `registerConnector` in `packages/naive/src/store/connectors/index.mjs`. The source map's `rules` are the source-of-truth matrix (EE-042, `packages/naive/src/store/connectors/resolve.mjs`): a system of record and owner per record type, attribute and context; `node packages/naive/src/checks/check-sources.mjs <dir>` refuses ties, and `node packages/naive/src/checks/check-where-used.mjs <dir>` reports where-used children that drifted from their parent. Every write through them appends to the venture's provenance log, `provenance.jsonl` (EE-031); `node packages/naive/src/checks/check-provenance.mjs <dir>` checks its hash chain, and `mentura baseline --venture <id>` adopts records written before the log. `node packages/naive/src/engine/need-now.mjs <venture dir>` says what a venture needs now (EE-028); `node packages/naive/src/engine/time-to-ready.mjs <venture dir>` measures time to running and ready; `node packages/naive/src/checks/check-team.mjs <dir>` checks team plans against the agent capability register (EE-029). Traces (EE-121): with `traces` on in `naive.config.json`, each run's steps are kept as OpenTelemetry GenAI spans in `<venture>/traces/<session>.jsonl`, hash-chained, and provenance lines name their span; `naive trace append` takes span lines from any harness on stdin, `naive trace show` prints a session as a tree, and `node packages/naive/src/checks/check-traces.ts <dir>` checks them (`node packages/naive/src/checks/traces-test.ts`). Agents reach records as files through `packages/naive/src/router/agent-files.ts` (EE-122): `ls`, `read`, `write`, `edit`, `glob` and `grep` over the router, so every write meets the gate and provenance (`node packages/naive/src/interfaces/tests/agent-files-test.ts`).
- Hosted mode: with `NAIVE_RUNTIME=hosted`, Naive reaches nothing outside the tenant. `packages/naive/src/core/runtime.mjs` is the one place that reads it. Environment commands (`NAIVE_JUDGE_CMD`, `NAIVE_SITE_CMD`, `NAIVE_TRACE_CMD`, `NAIVE_SYNC_*`, `MENTURA_*_CMD`) are ignored, the host registers `judge`, `site`, `trace`, `sandbox` and `git` hooks with `registerHook`, and each feature that needs a missing one (bash done-criteria, transcripts outside the venture, git, the discovery harness) refuses with a message naming it and why (`node packages/naive/src/interfaces/tests/hosted-runtime-test.ts`).
- `node packages/naive/src/engine/assess-problem.mjs <venture dir> [--as-is]` (route `purpose/validation/assess`) says what the problem's evidence is strong enough for: four assumptions labelled demonstrated to contradicted, the commitment they support (explore, prototype, charge, raise) and the next test, with no single score; it asks first when the record is incomplete (EE-050). `node packages/naive/src/engine/foundation.mjs <dir>` (route `purpose/foundation`) reports the strategic foundation by the Five Ws and How plus whether, and whose each is; `mentura confirm <statement>` and `mentura accept` of a foundation record need the name typed (EE-051).
- `node packages/naive/src/engine/freshness.mjs <venture dir>` (route `system/freshness`, `mentura freshness`) says which records are fresh, stale, expired or live holes: by time from freshness profiles (`packages/naive/src/engine/freshness.json`, overridden under `freshness` in `naive.config.json`, with per-phase profiles) and on demand when a dependency changed or a tag, path or package was revalidated (`mentura revalidate`, `verify`, `phase`; route `system/revalidate`). A stale record is still read, with a `freshness` flag; `--freeze <dir>` writes a shell that leaves live records as holes (Revalidating, V-1 to V-8; `node packages/naive/src/interfaces/tests/freshness-test.mjs`).
- `node packages/naive/src/checks/premise-lint.mjs <venture dir> [<route>] [--drafts] [--json] [--propose]` (`naive lint premises`) attacks the premises of a venture's goals, requirements, exit criteria, constraints and decisions. Questions are generated by formula from each record's fields and its graph, as state(record, field, aspect), with aspects undefined-term, unmeasurable, no-owner, unsupported-premise, orphan, conflict, dependency and phase-mismatch. Rules are off, warn (default) or error under `premise_lint.rules` in `naive.config.json`; it never edits a record, and `--propose` writes each finding as an open decision, and a rerun leaves a decision it already filed, or a person decided, as it is; measures are named `<goal>/<measure>`, and a bare measure id that two goals share is flagged (`node packages/naive/src/checks/premise-lint-test.mjs`).
- `node packages/naive/src/checks/check-detectors.ts <venture dir> [--json] [--propose]` checks a venture's detectors (`governance/detectors/<id>.json`) and their detection ledgers (`<id>.trials.jsonl`), with Naive's shipped defaults in `packages/naive/template/governance/detectors/` where the venture has no copy. It reports hit and false alarm rates with Wilson intervals, d' and c, ROC area, the base rate, and the expected cost at the current line and the best observed line (`packages/naive/src/engine/detection.ts`). It fails only on structure, never on a number: a schema error, a broken ledger chain, a line naming another detector or an unknown trial, an outcome the call cannot have, a no line on the wrong side of the yes line, costs that differ from the tier when `set_by` is `tier`, a one_way_door detector with a line or costs, an evidence source that is neither `venture` nor in `knowledge/sources.json`, and a person or record resolver, person sensor or check sensor module that does not exist. `--propose` files a criterion change as an open decision only when the tier is not one_way_door, at least 30 trials are resolved and a Wilson interval on the cost difference excludes zero; a rerun leaves a proposal it filed, open or decided, as it is, and it never edits a detector (`node packages/naive/src/checks/check-detectors-test.ts`).
- `node packages/naive/src/engine/decision-index.mjs <venture dir> [update|rebuild|read] [--since <iso>]` (route `system/decision-index`, `mentura index`) is the live decision index: the docket's ranking wrapped with structural impact for open decisions (`structural()` in `packages/naive/src/engine/impact.mjs`), phase weight, the requirement lift and violations from `foundation/requirements/*.json` when they exist; each run re-scores every active decision (an update equals a rebuild, so a passed due time re-ranks at once), caches in `.naive/decision-index.json` and appends rank history to `.naive/decision-index-history.jsonl` (`node packages/naive/src/interfaces/tests/decision-index-test.mjs`).
- The validation study (plugin beta first, Mentura later): interviews (`validation/interviews/[id]`), checkpoint feedback (`validation/feedback/[id]`) and bugs (`product/bugs/[id]`) are records; `node packages/naive/src/checks/check-validation-study.mjs <dir>` checks them across files and `naive bugs` (`packages/naive/src/engine/bugs.mjs`) lists open P0 and P1, the stable measure. The plugin beta's gate is `packages/naive/src/engine/beta-gate.mjs` over `beta/capabilities.json` (`naive beta status|feedback <capability>|unlock`): core (venture, docket, foundation) starts open, each later capability opens after feedback on the one before, unlock state is in `.naive/beta.json`, and the router refuses a locked route; it is on only with `beta.enabled` in `naive.config.json`. The tester is one id for the CLI and the router, `NAIVE_BETA_TESTER` (default `tester`), an anonymous id and never the acting role. `packages/naive/src/engine/feedback-route.mjs` routes feedback (Jev only when `beta.jev.send` is true, `beta.jev.set_by` names a person, `TYPESAFE_API_KEY` is set and a client is injected, accepted at 0.95, else a keyword fallback; no Jev client is built). `packages/naive/src/engine/telemetry.mjs` writes opt-in events (`packages/naive/src/records/telemetry.schema.json`, shared with Mentura) to `.naive/telemetry.jsonl`, which the router does not route, and sends only when `telemetry.send` is true and `telemetry.set_by` names a person; no sender is built. - `node scripts/dependency-rules.ts` checks the monorepo's dependency rules: no new import cycle between units (a unit is a tracked top-level folder until the code moves into workspace packages) and one version per dependency, peer and optional ones included, across the root `package.json` and its workspaces. An import is a relative `import`, `export ... from` or `require` whose target file exists, so an example path inside a string or a comment is not one. Today's cycles are listed in `scripts/dependency-rules.json` and the list may only shrink; its `leaves` are folders that import nothing else in the repository (`packages/naive/src/records`). Its `private` folders are imported only by their own files and their front door, the module of the same name beside them: `packages/naive/src/engine/signals`, the pure signal render, is one. `--graph` prints the import graph. `node scripts/dependency-rules-test.ts` breaks each rule on a copy.

The repository itself is never counted as temp space. `node packages/naive/src/checks/check-write-scope-test.ts` breaks it on a copy whose provenance code writes beside the repository.

A source with `carries: "signals"` whose connector is not the filesystem is read only with `confirmed_by` naming a person. `node packages/naive/src/interfaces/tests/signals-pull-test.ts` tests it end to end over two ventures.
- `node packages/naive/src/engine/generators/recipes-test.ts` tests the autoresearch record types (everything-ecosystem docs/design/AUTORESEARCH_RECORDS_2026-11-06.md, build plan item 3): a recipe (`<pattern>.recipe.ts`, form `typescript`, whose `packages/naive/src/records/recipe.schema.json` governs its exports), an eval plan (`<pattern>.plan.json`, addressed by its sha), the hash-chained experiment log (`<pattern>.experiments.jsonl`), receptions (`<record>.reception.json`) and `settles` on projected record types. The example recipe in `packages/naive/src/records/examples/signals/` renders the example record in the sandbox, the plan, log and receptions name its sha, the schemas refuse what the design forbids, each path has its kind, and each generator drafts a record that passes. Receptions and the signal pull through recipes are not built; recipes and the experiment log are written by the recipe route below.
- The recipe route `recipes/<pattern>` (`packages/naive/src/router/recipes.ts`, autoresearch build plan item 6): `mentura recipes/<pattern> read` gives the tip (the last kept candidate, else the live recipe) with its sha and the dev evaluations spent under the plan; `write` takes `{source, base}`, refuses a stale base, a candidate that is already the tip and a spent budget, asks the gate first, then scores the candidate against the tip inside the write (`scoreExperiment`) and appends one experiment line, written by the evaluator. A keep by an agent is held as a draft (the evidence package's gate rule `recipe-keeps-held`), a keep by a person is written live, a discard or fail is refused with its verdict, and a retry of the same plan, candidate and base returns the logged line and spends nothing. Every recipe-file write goes through it: `knowledge/recipe` and any write landing on a `*.recipe.ts` are refused naming `recipes/<pattern>`, and agent-files' write and edit of `/<pattern>.recipe.ts` are sent to the route. `node packages/naive/src/interfaces/tests/recipe-routes-test.ts` tests it.
- `node packages/naive/src/engine/recipes/sandbox-test.ts` tests the recipe sandbox (`packages/naive/src/engine/recipes/sandbox.ts`, autoresearch build plan item 4): `runRecipe(source, input, knobs, opts)` and `runRecipes` lint a recipe (size bound, no import, no literal holding a subject id or signal address), run a batch in one `node --permission` child with only `TZ=UTC`, a heap cap and a wall-time kill, give each call a fresh `vm` realm with no clock, randomness or code generation, and check one reception per heard signal. The clock, randomness, eval, imports, an endless loop, state between calls, the file system and the environment each fail closed. `vm` is not a security boundary, so this is layered defence (`packages/naive/src/engine/recipes/README.md`).
- `naive recipes plan <pattern> --by <person> [--weights uniform|cited] [--gap <duration>] [--min-gain <n>]` (`packages/naive/src/engine/recipes/cli.ts`, autoresearch build plan item 5) is a person's: it refuses an acting agent, draws purged training, dev and holdout as-of points, writes `<pattern>.plan.json` and freezes the eval set at `<venture>/_eval/<sha>/eval-set.json` (the points, the signal index, the facts as of each point and the settled outcomes). Only people and producers settle a claim: a person's local signal, or a producer's claim once a second producer reports it or a person states it; an agent's write settles nothing. `naive recipes check <pattern> [--json]` runs the recipe on the training rows in the sandbox and prints per-row losses, settled and predicted records, and noise disagreements found by ablation. Losses (exact, set-jaccard, abs-scaled), Brier, the seeded block bootstrap and the dev verdict are pure in `packages/naive/src/engine/recipes/scoring.ts`, outcomes in `outcomes.ts`. `node packages/naive/src/engine/recipes/scoring-test.ts` and `node packages/naive/src/engine/recipes/eval-set-test.ts` test them: windows purged, an agent's write resolves nothing, the verdict identical over two runs.
- `naive recipes search <pattern> [--factor 2] [--shrinks 2] [--max-writes 200] [--json]` (`packages/naive/src/router/orchestration/recipe-search.ts`, autoresearch build plan item 10) improves a recipe with no model: coordinate descent over its knobs, one step each way per knob (`packages/naive/src/engine/recipes/knobs.ts`: numbers by the factor, booleans flipped, rating floors one grade), each step an experiment write to `recipes/<pattern>` as the agent `knob-search`, so the router scores it and holds a keep as a draft; a pass with no keep takes the square root of the factor up to `--shrinks` times, and the plan's dev budget stops it. `node packages/naive/src/interfaces/tests/recipe-search-test.ts` shows a fixture venture improving; `node packages/naive/src/engine/recipes/knobs-test.ts` tests the knobs. Probes (`packages/naive/src/engine/recipes/probes.ts`, `research.probe_rate` in `naive.config.json`, 0 by default): a deterministic share of noise receptions per record marked `probe: { rate }`, and `ipwEstimate` scores a candidate on them by inverse propensity (`node packages/naive/src/engine/recipes/probes-test.ts`); the pull marking them in reception files is not built.
- `node packages/naive/src/engine/detection-test.ts` tests the signal detection arithmetic in `packages/naive/src/engine/detection.ts`: hit and false alarm rates with Wilson intervals, `d'`, `c` and beta (log-linear correction), the optimal beta* from costs and a base rate, ROC area, expected cost and the best criterion. It is pure: no I/O, and no records.
- `node packages/naive/src/router/detection-ledger-test.ts` tests the detection ledger written through the router (`packages/naive/src/router/detection-ledger.mjs`, route `governance/detector-trial/<id>` with action `append`): with `governance/detectors/gate-confidence.json` in a venture, a held draft a person accepts resolves the gate's yes call as a false alarm, a passed write a person reverts (`mentura <route> write --as person --revert`) resolves its no call as a miss, the chain holds after parallel appends, and a duplicate or unknown resolution is refused. Without the file nothing is written.
- `node packages/naive/src/interfaces/tests/as-of-test.ts` tests the blob store and as-of reads: every write through the router stores the bytes its provenance line names under `<venture>/.naive/blobs/` (`packages/naive/src/core/blobs.mjs`, keyed by the line's `sha256`, written before the line), and `readAsOf(dir, routeOrPath, t)` in `packages/naive/src/store/as-of.mjs` returns a record as it was at transaction time t and nothing later, or null before its first write or for a version written before blobs existed (nothing is backfilled); `pathsAsOf(dir, t)` lists the paths it answers for.
- `node packages/naive/src/interfaces/tests/reads-as-of-test.ts` tests the researcher's read clamp (`packages/naive/src/router/reads-as-of.mjs`): a `<function>-researcher` role reads through the router and `packages/naive/src/router/agent-files.ts` only as of `reads_as_of` (or `MENTURA_READS_AS_OF`), from the blob store and never the live files, with no signal observed after the cut; with no cut its reads are refused; as of a cut only read, view, write, append and template are allowed; writes are not clamped; and no agent reads or writes `_eval/`.
- `node packages/naive/src/interfaces/tests/research-programs-test.ts` tests research programs (autoresearch build plan item 11): `programs/<function>.md`, record type `research-program` with `writer: "person"`, route `operations/research-program/<function>`. A person writes it whole (`mentura operations/research-program/<function> write --as person --input <file.json>` with `{ "text": "..." }`) and it lands live with provenance and its bytes in the blob store; every agent's write is refused before anything else (rule person-only in `writerRule`, `packages/naive/src/engine/gate.mjs`), a `<function>-researcher` included, through the router and `packages/naive/src/router/agent-files.ts`. A researcher reads its own function's program live and everything else as of its cut. Each function module ships `templates/research-program.md`, which `packages/naive/src/engine/research-programs.mjs` copies into a venture once, when venture.json departments lists the function and the file is missing: through `packages/naive/src/engine/add-department.mjs` (so `init-venture.mjs --type`) and `naive upgrade`. The loop a researcher runs is Naive's one generic research skill, `packages/naive/src/interfaces/skills/research/SKILL.md`.
- `node packages/naive/src/engine/bdd.mjs <file.feature>` runs Gherkin behaviors as tests, with step definitions in `<file>.steps.mjs`; behaviors are written first (EE-050).
- `node packages/naive/src/functions/products/frameworks/product-anatomy/test.mjs` tests the Product Anatomy runner's role rules.
- `node packages/naive/src/checks/test.mjs` tests the checkers on broken copies; `node packages/naive/src/records/validate.mjs` validates every record against its schema.

## Docs

- The docs (docs/, every SKILL.md, and docs/master/naive-docs.md, exported from the master article) state only what is decided and built. Something not built says "not built" in that sentence.
- Ideas go through `naive capture`, not into the docs.
- READMEs are docs as code: each sits next to the code it describes, the code is the source of truth, and new ones follow `docs/readme-template.md`. READMEs link each other with relative links, which work on GitHub and in an editor.
- Every PR updates the docs or starts a line of its body with "No docs change: " and a real reason (a placeholder, a blank reason or the phrase quoted mid-line does not count); .github/workflows/docs-required.yml enforces it. Code here means any file that is not `.md` or `.mdx`, so JSON, CSV and images count. A PR that changes code under `packages/`, `schema/`, `interface/`, `packages/naive/library/packages/` or `purpose/` must update the README nearest that code, searched up to its top-level folder (`node packages/naive/src/checks/check-docs-claims.mjs --readmes` lists the ones owed). Only the docs `packages/naive/src/checks/check-docs-claims.mjs` scans count (`--scanned` lists them): `docs/master/*.md`, `packages/naive/library/packages/*/playbooks/*.md`, every SKILL.md and every README.md.
- `node packages/naive/src/checks/check-docs-claims.mjs` must pass: every command, flag, repository path and route the docs name exists in the code, and every relative Markdown link, inline or reference-style, resolves. HTML `href` and `src` are not checked.

## TypeScript

Naive is moving from JavaScript to TypeScript in four phases: type-check the JavaScript, generate record types from `packages/naive/src/records/*.schema.json`, rename modules to `.ts` folder by folder, then publish compiled JavaScript. Until that is done:

- New files are `.ts`. They run under Node's type stripping, so they use erasable syntax only: no `enum`, no `namespace`, no parameter properties (`erasableSyntaxOnly` in `tsconfig.json` enforces it). Import another `.ts` file by its `.ts` name.
- A record's type comes from its JSON Schema, never typed by hand.
- No `any` in new code. Use `unknown` and narrow it.
- Existing `.mjs` files are converted in their phase, not inside unrelated PRs.

## Rules

- Never read or print `.env*` files.
- Schema decisions are logged in `docs/decisions/decisions.json` and cited by id (`EE-NNN`). The schema never cites a decision from any instance.
- Torian merges. Agents open draft PRs and do not merge.

## Tooling

Every layer has `packages/naive/src/records/layers/<layer>/tooling/integrations.json`: the tools and services it can use, each checked against `packages/naive/src/records/integration.schema.json` (status in-use, candidate or rejected; interfaces such as files, MCP, API, SDK; credentials by variable name only). Agent runtimes (Claude Agent SDK, Cursor Agent SDK) are listed under `execution/tooling/`. The interface layer is narrower: an interface lets a person, with agents, work across at least three of the five other layers in one session. Agent harnesses (Claude Code, Cursor, Codex) are the default kind; the operator console is a custom one. A tool serving one or two layers (Obsidian, Linear) is an integration of those layers. `node packages/naive/src/checks/check-integrations.mjs` enforces this.

Choosing tools is opt-in: when someone wants help, `packages/naive/src/functions/it/skills/tool-selection/SKILL.md` gives the principles for the questions and the scoring (Jev plus a reasoning model), and each layer's `tooling/questions.md` gives its dimensions and example questions. Knowledge has one so far.

## Ventures

The ecosystem is a schema; a workspace is an instance made of ventures (EE-002, EE-011). A venture is anything a builder undertakes, at a phase from Discovery to Platform (EE-012); personal life is out of scope (EE-009). Each venture has a `venture.json` (`packages/naive/src/records/venture.schema.json`), product cards in `products/`, account records in `accounts/` where it keeps them (EE-021), and the three pillars. Create one with `node packages/naive/src/engine/init-venture.mjs`; check a workspace with `node packages/naive/src/checks/check-ventures.mjs <dir>`. Work in a venture runs as handoffs (`execution/handoffs/`), proved by evidence (`evidence/results/`), under its decision rights (`governance/decision-rights.json`). The example ventures are in `packages/naive/src/records/examples/` (`packages/naive/src/records/examples/workspace/` and `packages/naive/src/records/examples/software/`); real ventures live in their tenants' own stores, outside this repository. Every record type is indexed in `packages/naive/src/engine/README.md` and listed, with its owning layer, in `packages/naive/src/records/data-model.json`. Each layer's manifest (skills, records it still owns, reads and writes) is in `packages/naive/src/records/layers/<layer>/layer.json`. Venture packages are `packages/naive/library/packages/<name>/package.json`. A kit is Mentura's enhanced package, kept in Mentura and found through `NAIVE_KITS` (EE-071). See `docs/design/LAYERS_AND_KITS_2026-10-27.md`. Design: `docs/design/VENTURES_2026-10-27.md`.

## Nouns and references

Standards first (EE-014): use an established term with its standard meaning, and coin one only when none exists. `packages/naive/src/terms/ontology.json` is canonical for nouns (`packages/naive/src/terms/ontology.md` is its readable form); `node packages/naive/src/checks/check-nouns.mjs` fails when a retired noun reappears, when a noun has no standard, or when a function's capabilities are not nouns it owns. Each noun names its function, or null when the word is shared. Each layer keeps the sources behind its defaults in `packages/naive/src/records/layers/<layer>/references/references.json`; `packages/naive/src/functions/capabilities/skills/find-reference/` fills and re-checks them.
